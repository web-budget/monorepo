# CLAUDE.md

Este arquivo orienta o Claude Code no `client/`, o frontend do webBudget: Vue 3 com `<script setup>` e TypeScript 6.0, Vite 8, Vue Router 5, Pinia 4, vue-i18n 11, axios, shadcn-vue (Reka UI e Tailwind 4), vee-validate com Zod, Vitest 5, ESLint 10, oxlint e Prettier, sobre Node 24 e pnpm 12. O alias `@` aponta para `src/`. As regras do repositório inteiro (issues, branches, PRs, idioma, comentários no código, como ativar o Node e o pnpm nesta máquina e a proibição de subir os servidores de desenvolvimento do usuário) estão no `CLAUDE.md` da raiz e valem aqui também.

## Comandos

O `engines.node` do `package.json` exige o Node 24.15 ou mais novo, e o `packageManager` fixa o pnpm 12.21.0. Rode tudo a partir de `client/`:

```bash
pnpm install         # instala as dependências (o CI usa --frozen-lockfile)
pnpm dev             # Vite em http://localhost:8086, com proxy de /private para http://localhost:8085
pnpm build           # roda type-check e build-only em paralelo; falha se qualquer um falhar
pnpm type-check      # vue-tsc --build sobre as referências do tsconfig.json (app, node e vitest)
pnpm test            # Vitest em modo watch num terminal interativo: não termina sozinho
pnpm test:run        # Vitest numa passada só
pnpm test:coverage   # Vitest numa passada só com cobertura v8, grava client/coverage/ e confere o piso
pnpm lint            # oxlint . --fix, depois eslint . --fix --cache
pnpm format          # prettier --write em src/ inteiro (veja a regra do Prettier abaixo)
```

O `vite.config.ts` fixa a porta 8086 com `strictPort: true`: se ela estiver ocupada, o `pnpm dev` falha em vez de escolher outra porta. A 8086 é do servidor de desenvolvimento do usuário; para verificar algo, suba um Vite descartável com `pnpm dev --port <outra>` e pare-o depois (regra da raiz). O proxy de `/private` continua apontando para a 8085, e com o server parado as chamadas a `/private` respondem 502.

O `pnpm test` só fica em modo watch quando o terminal é interativo (TTY). Sem TTY, ou com `CI=true`, o Vitest cai para uma passada só e termina. Não conte com isso: em scripts, no CI e nas verificações do Claude use `pnpm test:run` ou `pnpm test:coverage`, que nunca ficam esperando.

O CI (job `test-client` de `.github/workflows/ci.yml`) roda `pnpm install --frozen-lockfile`, `pnpm lint`, `pnpm build` e `pnpm test:coverage`, nessa ordem. Rode os três últimos antes de abrir um PR que mexe no `client/`. O CI não confere o Prettier, e o ESLint usa o `eslint-config-prettier`, então o `pnpm lint` também não reclama de formatação.

**O Prettier roda só nos arquivos que você tocou.** Formate o que mudou com `pnpm exec prettier --write <arquivos>`, nunca com `pnpm format` nem com `prettier --write src/` num PR. O `src/` está formatado hoje, mas um formatador rodado na árvore inteira espalha pelo diff mudanças em arquivos que o PR não tem motivo para tocar, e elas precisam ser desfeitas à mão. Se um arquivo tocado já estava fora do padrão no `HEAD`, mantenha formatados só os seus próprios trechos em vez de reformatar o arquivo inteiro. O estilo vem do `.prettierrc.json`: sem ponto e vírgula, aspas simples e 100 colunas.

O `tsconfig.app.json` estende o `@vue/tsconfig` (que já liga o `strict`) e acrescenta `noUncheckedIndexedAccess`, `noUnusedLocals` e `noUnusedParameters`, então um import ou uma variável sem uso quebra o `pnpm build` e o `pnpm type-check`. Os testes são checados pelo `tsconfig.vitest.json`, e o `tsconfig.app.json` os exclui.

**O TypeScript fica na linha 6.0.** O TS 7 não serve aqui: ele deixou de exportar `typescript/lib/tsc`, o que derruba o `vue-tsc` 3, e o typescript-eslint se recusa a carregar com ele (o peer dele é `>=4.8.4 <6.1.0`). O TS 6.0 é a linha que as duas ferramentas suportam, por isso o `package.json` pede `~6.0.0`. Pelo mesmo motivo nenhum `tsconfig` tem `baseUrl`: o TS 6 rejeita a opção com o erro TS5101, e o alias `@/*` não precisa dela, então não a acrescente.

## Testes

**Arquivos de teste terminam em `.test.ts`, nunca em `.spec.ts`.** O `vite.config.ts` fixa `test.include` em `src/**/*.test.ts`, então um arquivo com outro sufixo nunca roda, e ninguém percebe. Os testes ficam **ao lado** do código que cobrem; não existem diretórios `__tests__/`, e nenhum deve ser criado.

O ambiente é o `jsdom`, e o `src/test/setup.ts` roda antes de cada arquivo (`test.setupFiles`) com o `enableAutoUnmount(afterEach)`, então nenhum teste precisa desmontar o que montou. Os `globals` do Vitest estão desligados: importe `describe`, `it`, `expect` e `vi` de `'vitest'` em cada arquivo. O `setup.ts` também põe no jsdom o que o shadcn-vue e o Reka UI esperam e ele não tem (`ResizeObserver`, `matchMedia` e `scrollIntoView`), e o `src/test/mounting.ts` tem os helpers de montagem: `createTestPlugins()` devolve o router (em memória), o `createTestingPinia` e o i18n prontos para o `global.plugins`, e o `mountInSidebar()` monta um componente dentro do `SidebarProvider`, que o menu lateral e a barra superior exigem. Menus e diálogos do Reka UI vão para o `document.body`: monte com `attachTo: document.body` e procure o conteúdo lá, e abra o menu do usuário com `keydown` Enter, porque o `pointerdown` não abre no jsdom.

O Pinia tem uma regra que decide sozinha:

| O teste | Usa |
|---|---|
| monta um componente | `createTestingPinia()` do `@pinia/testing`, passado em `global.plugins` |
| exercita um store ou um composable direto | `setActivePinia(createPinia())` no `beforeEach` |

O `createTestingPinia()` troca todas as ações por spies, que é o que um teste de componente quer: as ações viram algo para conferir e nenhuma chamada à API escapa. Passe `{ stubActions: false }` só quando o comportamento testado *é* a ação de verdade rodando. Os testes de store mockam o módulo da API com `vi.mock('@/api/<recurso>')`, como em `src/stores/auth.test.ts`.

Duas armadilhas disso: sob o `createTestingPinia`, `hasRole` do `auth` também vira spy, então um teste de componente ou de guard que depende de role precisa de `vi.mocked(auth.hasRole).mockImplementation(...)`, senão toda seção some. E o store `auth` importa o router, então o `auth.test.ts` mocka `@/router` com `vi.mock`.

Confira o que aparece na tela, os eventos emitidos e as interações do usuário, nunca o `wrapper.vm` ou métodos privados, que prendem o teste à implementação e quebram na primeira refatoração. Nada de teste só de snapshot: um snapshot que ninguém lê continua passando com a funcionalidade quebrada.

A cobertura é medida pelo `pnpm test:coverage` (provider v8, relatório em `client/coverage/`) e **imposta**: `coverage.thresholds` no `vite.config.ts` define um piso para statements, lines, functions e branches, e o CI roda esse comando, então um PR que derruba qualquer um dos quatro abaixo do piso quebra o build. O piso hoje é **100% nos quatro**. Ficam fora do conjunto medido os arquivos de teste, `src/test/**`, `src/main.ts`, `src/types.ts`, `src/api/**` e `src/components/ui/**` (o código que a CLI do shadcn-vue gera).

**A catraca:** um PR pode subir esses números, nunca baixar. Um PR que acrescenta testes pode subir cada piso até o valor inteiro (arredondado para baixo) que o seu próprio `pnpm test:coverage` reporta; um PR que não muda a cobertura deixa os números como estão. A única forma de fazer uma queda de cobertura passar no CI é baixar um piso, e um PR nunca faz isso. Com o piso em 100, a regra que vale na prática é essa: código novo chega com os testes que o cobrem por inteiro, inclusive os dois lados de cada `?.` e `??` que o v8 conta como branch.

## Convenções de código

**Nada de nomes abreviados.** Use nomes completos e descritivos para variáveis, props, iteradores de laço e variáveis locais de composables.

| Evite | Use |
|---|---|
| `w in wallets` | `wallet in wallets` |
| `cc`, `fp` | `costCenter`, `financialPeriod` |
| `qty`, `pct`, `amt` | `quantity`, `percentage`, `amount` |
| `res`, `err`, `e` | `response`, `error` |

**Código não leva comentários.** É a regra da raiz e vale aqui: se algo precisa de comentário, renomeie ou reestruture. A única exceção é um porquê não óbvio que o código não consegue expressar, como o contorno de um bug de dependência.

Componentes usam a Composition API com `<script setup lang="ts">`, na ordem `<script>`, `<template>`, `<style>`. Stores são escritos no estilo de composição do Pinia (`defineStore('nome', () => { ... })`).

## Arquitetura

O client fala só com o server do monorepo, pela mesma origem: em desenvolvimento, o Vite encaminha `/private` para a 8085. Não há CORS, não há URL de API configurável por variável de ambiente e não há token no client.

O client tem as camadas não visuais (#19) e a base visual (#22): shadcn-vue, o shell com as rotas por seção e os componentes compartilhados. As telas de autenticação e de erro (#23) existem (veja [Telas de autenticação e de erro](#telas-de-autenticação-e-de-erro)) e os cinco cadastros (#24) também (veja [Cadastros](#cadastros)), assim como a administração de usuários (#32, veja [Administração de usuários](#administração-de-usuários)); a página inicial de cada módulo é uma capa com cartões de atalho (veja [Layout e rotas](#layout-e-rotas)) e os dashboards são um espaço reservado, à espera do épico do financeiro (#34).

### API (`src/api/`)

**O `src/api/` é a única camada que usa o axios.** Stores, composables e componentes chamam as funções de um módulo daqui e nunca importam o axios nem o `apiClient` direto.

O `src/api/client.ts` cria o `apiClient` com `baseURL: '/private/v1'` (sempre na mesma origem, nunca com host) e `timeout` de 20 s. O interceptor de resposta converte toda falha num `ApiError`, com `status` (`null` quando a requisição nem chegou ao server, e `isNetworkError` para perguntar isso), `error` (o código do `ProblemDetail` do server), `detail`, `parameters` e o erro original em `cause`. Cancelamentos e erros que não vêm do axios passam sem conversão. O interceptor não mostra nada na tela: o toast padrão para um `ApiError` vem do `plugins/apiErrorHandler.ts` (veja [Notificações e confirmações](#notificações-e-confirmações)). Uma chamada que trata o erro por conta própria passa `silent: true` na configuração do axios e o plugin a ignora, como o `fetchSession` faz.

O `client.ts` também cuida de duas coisas da sessão (veja [Autenticação](#autenticação)): carimba a hora de toda resposta que o server deu, sucesso ou erro, em `api/serverActivity.ts` (é o que o `useInactivityLogout` lê), e garante o token de CSRF antes de uma escrita. O `client.ts` não importa o store nem o router, porque o `api/auth` importa o `client` e o store importa o `api/auth`: tudo o que navega ou mexe na sessão fica no `plugins/apiErrorHandler.ts`.

Há um arquivo por recurso do server (`auth.ts`, `accounts.ts`, `users.ts`, `roles.ts` e um por cadastro); os endpoints estão neles e nos controllers do server. O que não se lê no código:

- `login` e `linkGoogle` (de `auth.ts`) devolvem um `LoginOutcome`, e o **código HTTP** decide: 200 é a sessão e 202 é `needs_enrollment` ou `needs_totp`, porque o corpo de uma sessão também tem um `status`.
- O `GET /auth/config` é `silent`, como o `fetchSession`.
- O `findAll` de `users.ts` traduz as abas de aprovação (`PENDING`, `APPROVED`, `BLOCKED`) para o parâmetro `userStatus` do server, porque o `status` dele é o filtro de ativo e inativo.
- Os módulos de cadastro têm a forma de `CrudApi` (`src/composables/useCrudResource.ts`): `findAll`, `findById`, `create`, `update` e `remove`.

### Tipos (`src/types.ts`)

Todos os formatos que atravessam a API ficam em `src/types.ts`, num arquivo só, com os nomes da v4: `<Entidade>CreateForm` e `<Entidade>UpdateForm` para o que vai, `<Entidade>View` e `<Entidade>ListView` para o que volta. Também ficam lá o `PagedResponse<T>` (o envelope `PagedModel` do Spring: `{ content, page: { size, number, totalElements, totalPages } }`), o `PageQuery` (`filter`, `status`, `page`, `size`, `sort`), o `ProblemDetail` e os tipos da sessão (`SessionResponse`, `Role`, `UserStatus`).

### Stores (`src/stores/`)

Há um store por assunto (`auth`, `language`, `appearance`, `trustedDevices`, `account`, `usersAdmin` e um por cadastro); as ações estão em cada arquivo. O que não se lê no código:

- `auth.login` e `auth.linkGoogle` devolvem o `LoginOutcome` e só guardam a sessão quando ele é `authenticated`; `auth.restoreSession` devolve se há sessão (veja [Autenticação](#autenticação)).
- O `language` é quem aplica o idioma ao `i18n`, ao `lang` do `<html>` e ao `localStorage`; `auth.changeLanguage` grava no perfil e guarda a `SessionResponse` que o server devolve (veja [i18n](#i18n-srclocales)).
- O `usersAdmin` abre com o status `APPROVED`, uma aba de aprovação, e não `ACTIVE`.
- `wallets` e `costCenters` acrescentam `findByName` e a lista de opções que ele preenche, para o `SearchSelectField`.

Os stores de cadastro montam tudo sobre o composable `useCrudResource`, que guarda o `pageRequest`, o `pageResponse` e a entidade corrente e conta as operações em andamento para o `loading`. Um store novo de CRUD usa o mesmo composable em vez de reescrever essa mecânica.

- **Carregamento sob demanda:** cada store é carregado pela view ou pelo componente que precisa dele, no `onMounted`. Cargas em paralelo numa mesma tela usam `Promise.all`.
- **Atualização pessimista:** toda mutação espera a resposta da API antes de mudar o estado do store. Não há atualização otimista nem rollback.
- **Ações devolvem promessas e propagam o `ApiError`.** Não há os callbacks `onSuccess`/`onError` da v4: quem chama usa `await` e `try`/`catch`.
- **`reset()` no fim da sessão:** todo store que guarda dado do usuário tem um `reset()`, e o `stores/resetUserStores.ts` chama todos eles. O `auth` chama o `resetUserStores()` em toda saída de sessão (todos passam pelo `clearSession()`: o `restoreSession()` que falha, o `logout()` e o `expireSession()`) e também no `login()`, antes de guardar a sessão nova: nenhum usuário começa vendo o que o anterior carregou. Um store novo com dado do usuário ganha um `reset()` e uma linha lá.

### Composables e utils

- `src/composables/useCrudResource.ts`: a mecânica comum dos stores de cadastro (veja acima).
- `src/composables/useInactivityLogout.ts`: o logout por inatividade, iniciado no `App.vue` (veja [Autenticação](#autenticação)).
- `src/composables/useModuleCounts.ts`: recebe um mapa de destino para uma função que devolve a contagem (ou `null`) e preenche o `counts` ao montar, uma contagem por vez, para as capas dos módulos.
- `src/composables/useNotification.ts` e `src/composables/useConfirmDialog.ts`: toasts e confirmação de exclusão (veja [Notificações e confirmações](#notificações-e-confirmações)).
- `src/composables/useCrudList.ts`, `useCrudForm.ts`, `useCrudDetail.ts` e `useServerErrors.ts`: a mecânica das telas de cadastro (veja [Cadastros](#cadastros)).
- `src/composables/useListFilters.ts` e `src/utils/listQuery.ts`: a URL como dono do estado das listas (veja [Filtros na URL](#filtros-na-url)).
- `src/utils/handledErrors.ts`: `markHandled` e `isHandled` guardam, num `WeakSet`, os erros que uma tela já mostra no alerta do topo, para o `apiErrorHandler` não repeti-los em toast.
- `src/lib/utils.ts`: o `cn`, que junta classes e resolve conflitos do Tailwind. O shadcn-vue o importa de `@/lib/utils`.
- `src/utils/pageRequest.ts`: o `PageRequest` do client (`filterText`, `status`, `current`, `size`, `direction`, `sortField`), o `createPageRequest` (página de 15, ordem padrão por `createdOn` decrescente, as constantes `DEFAULT_SORT_FIELD` e `DEFAULT_SORT_DIRECTION`), o `createPageResponse` e o `toPageQuery`, que traduz um para o `PageQuery` da API.
- `src/utils/apiErrorNotice.ts`: o `describeApiError` traduz um erro em chaves do i18n, com parâmetros e severidade (`warn` ou `error`), para quem for mostrá-lo. Devolve `null` para 401 e 403, que são tratados por navegação (a exceção é o 403 `invalid-csrf-token`, que tem aviso próprio), e cai na mensagem genérica quando o código de erro ou o campo em conflito não tem tradução, para que nenhuma chave crua chegue à tela.
- `src/composables/useAuthConfig.ts`: busca o `GET /auth/config` ao montar e expõe `googleAuthEnabled`, que fica `false` enquanto carrega e quando a chamada falha (veja [Telas de autenticação e de erro](#telas-de-autenticação-e-de-erro)).
- `src/utils/passwordRules.ts`: as regras de senha do client (de 8 a 128 caracteres, uma maiúscula e um número), usadas pelo `recoverPasswordSchema` e pela lista de requisitos.
- `src/utils/safeRedirect.ts` e `src/utils/queryValue.ts`: o filtro do `redirect` do login e a leitura de um parâmetro de query como texto (veja [Telas de autenticação e de erro](#telas-de-autenticação-e-de-erro)).
- `src/utils/localDate.ts`: `parseLocalDate` e `formatLocalDate` convertem as datas `yyyy-mm-dd` da API sem passar pelo UTC.

Um composable reutilizável vai em `src/composables/`; uma função pura sem estado reativo vai em `src/utils/`.

### Componentes

Os componentes se organizam pelo papel, não pela view que primeiro precisou deles:

As pastas de `src/components/` e o que cada uma guarda:

- `ui/`: os primitivos do shadcn-vue, já ajustados ao Caderno verde (veja [Estilos](#estilos)); ficam fora da cobertura, então não escreva testes para eles. **Estão editados à mão:** rodar `shadcn-vue add` sobre um que já existe sobrescreve as variantes do design, então confira o diff e refaça o ajuste.
- `brand/` (a marca), `layout/` (o shell, o registro de seções `sections.ts` e os layouts por seção), `auth/` (as etapas das telas de conta), `devices/`, `icons/`, `listing/` (tabela, busca, abas de situação), `common/` (cabeçalho, cartões, moeda e data), `users/` (as peças da tela de usuários) e `forms/` (campos e o cartão do formulário). A raiz tem a `PageStructure` e a `ErrorPage`.
- `icons/GoogleMark` tem cores fixas, as da marca do Google: é a exceção à regra dos tokens.
- `forms/PasswordInput` repassa os atributos ao `<input>`, então vai dentro de um `FormControl`.

Um componente reutilizável e só de apresentação vai num diretório compartilhado, não ao lado do primeiro uso.

**Props e eventos da v4 foram mantidos** nos componentes de `listing/`, `common/` e `forms/`, para que as views de cadastro (#24) sigam o desenho da v4. O que muda é só o que o PrimeVue fazia por baixo:

- `ItemsTable`: no lugar das `<Column>` do PrimeVue, recebe a prop `columns` (`{ field, header, sortable?, class?, align?: 'end', mono?, wide? }`, com `header` já traduzido; `align: 'end'` e `mono` servem às colunas de valor, e `wide` faz o detalhe ocupar a linha inteira do cartão no celular). Uma célula customizada vem pelo slot `cell-<campo>` (`{ item, value }`) e a coluna de ações pelo slot `actions` (`{ item }`); sem o slot `actions` a coluna não existe. A coluna Situação (a de `active`, ordenável) vem por último, antes das ações, e some com `:show-status="false"`. Com `detail-route` (o nome da rota de detalhe, `wallets.detail`), a primeira coluna (ou a de `link-field`) vira link para o detalhe, e o conteúdo do slot fica dentro do link. Os eventos são os da v4: `pageChanged` (`{ currentPage, pageSize }`, com `currentPage` **começando em zero**, como o `pageRequest.current`), `rowSelected` (`{ data, index }`, no clique na linha; clicar no link ou nas ações não o dispara) e `tableSorted` (`{ sortField, sortOrder: 'asc' | 'desc' }`; ao remover a ordenação volta para `createdOn` decrescente, o padrão do `createPageRequest`). A prop `currentPage` (zero-based) marca a página atual e `loading` mostra o esqueleto; `sortedField` e `sortedOrder` dizem qual coluna está ordenada (o `createdOn` decrescente, o padrão, não marca nenhuma). Abaixo de 768px (`useMediaQuery`) a tabela vira cartões com os mesmos slots; o rodapé mostra `1–15 de 40` (ou o texto da prop `summary`, "N carteiras encontradas para “texto”", quando há busca aplicada) e a paginação e, só com mais de 15 registros, o seletor de linhas por página. Uma coluna com `mobile` (`title`, `value`, `line` ou `hide`, mais `mobileLabel: false` para esconder o rótulo da linha) liga o layout compacto do celular, o do financeiro: um cartão só com uma linha por registro (nome à esquerda, valor e "…" à direita e, embaixo, a linha miúda "Vencimento: 05/11/2026 · Casa · Moradia · Pago"); sem `mobile` em nenhuma coluna a tabela continua virando um cartão por registro. A prop `noun` ("movimentos") entra no rodapé ("1–15 de 33 movimentos"), `defaultSortField` diz qual é a ordem padrão da tela (a coluna ordenada que não vai para a URL) e `activeSortIconOnly` tira o ícone de ordenação das colunas que não estão ordenadas (e mostra o da coluna ordenada mesmo na ordem padrão), como no mock do financeiro; `statusSortable` (padrão verdadeiro) deixa a coluna Situação ordenável, e `srOnly` na coluna deixa o título só para leitor de tela. O slot `cell-<campo>` do título do cartão compacto recebe `compact: true`, para a célula mostrar outra coisa no celular (a transferência mostra "Origem → Destino"). `hideFooter` tira o rodapé (a contagem e a paginação), para a tabela de compras do detalhe de uma fatura, que é uma lista inteira sem página. O componente é genérico no tipo da linha (`T extends { id: string; active?: boolean }`), então o `item` dos slots chega tipado.
- `SearchControls`: os mesmos `v-model:status` e `v-model:filter` e os eventos `onFilterChange` e `onFilterReset`. Busca à esquerda, num `<form role="search">` de até 672px (`max-w-2xl`) com o campo de 40px (`h-10`, texto de 15px) e a lupa no fim dele como o botão de buscar (`type="submit"`, `aria-label` "Buscar", num bloco com `border-l` e `bg-muted`; não há botão de texto ao lado). Só dispara com Enter ou com a lupa, nunca a cada tecla; o X, entre o texto e a lupa, limpa só o texto e abas de situação à direita, com `statusOptions` (`MASCULINE_STATUS_OPTIONS` ou `FEMININE_STATUS_OPTIONS`; começam pela situação mais usada e terminam em Todos/Todas) e `counts` (a contagem em mono de cada aba; sem opções, `statusOptions` vazio, as abas nem aparecem); o slot padrão entra na mesma linha, depois das abas (o select de tipo dos recorrentes). **A ação principal ("Criar") não fica aqui:** vai no `PageHeader`.
- `ActionButtons`: o menu "…" da linha, com Editar e Excluir; emite `onEdit` e `onDelete`.
- `ListState`: o estado da lista que não é tabela, com `kind` (`empty`, `no-result` ou `error`), `entity` (o prefixo do i18n), `icon`, `query` e `message`; emite `create`, `clear` e `retry`. Os textos vêm de `<entidade>.list.*` e de `crud.list.*`; a prop `copy` troca os que o mock escreve de outro jeito (inclusive `emptyAction`, o texto do botão do estado vazio) e `outlineAction` faz o botão do estado vazio sair pequeno, de contorno e sem o "+", como o do mock das faturas ("Criar", que leva a um período novo).
- `PageContainer` só empilha os blocos da página (`grid grid-cols-1 gap-5`, a largura é a toda da área ao lado do menu lateral, sem teto; aceita `class` para trocar o espaço, e as listas passam `gap-6`, os 24px que o design põe entre o cabeçalho e a busca); `PageHeader` tem o título (`text-2xl leading-9`, a linha de 36px é a altura dos botões `h-9`, e título e botões ficam alinhados pelo topo, `items-start`), a descrição (só a lista leva; o detalhe mostra só o nome e a situação, sem repetir o que o formulário já mostra) e, nos slots, o `badge` (ao lado do título) e as `actions` (no máximo uma ação primária; as secundárias vão em botão de contorno ou no menu).
- `StatusToggle`: recebe o `name` (mais `label` e `hint`) e se liga ao formulário pelo `useField` do vee-validate, então vai dentro de um `useForm`; é um `Switch` com o texto "Situação" acima (a situação ativo/inativo da edição não usa o `StatusToggle`: tem o `StatusSection`, abaixo) (`heading` troca esse texto e `class` ajusta o encaixe na grade, por exemplo `md:col-span-1`; os usuários o usam também para o envio do e-mail de ativação). Os títulos de todos os blocos (`FormSection`, `DetailSection` e `StatusSection`) são `text-base font-semibold`, como o `section-title` do design. A ordem dos blocos é a mesma no formulário e no detalhe: Situação (só na edição), depois o que identifica o registro, depois o que depende do tipo (dados do banco, carteira ou fatura do cartão) e por fim valores e metas (orçamento, datas e metas, saldo no detalhe da carteira). O `FormSection` tem `stacked` (título em cima dos campos, para formulários com coluna lateral), o `InputField` tem `hint` (o texto de ajuda abaixo do campo) e o `FormCard` aceita os slots `badge` (ao lado do título) e `aside` (uma coluna de 280px à direita do formulário, que desce para baixo dele no celular; com `wide-aside` a coluna é de 320px e só abre ao lado a partir de 1280px, como o quadro dos períodos). `StatusSection` é o bloco da situação das edições: `name`, `label` (o texto do switch: "Ativa", "Ativo", "Cadastro ativo") e `hint` (a ajuda sob o título "Situação", à esquerda; o switch fica à direita, centralizado na vertical); é compacto (`py-3.5`, mais baixo que um `FormSection`) e vai **antes** de todos os `FormSection`, com `v-if="updating"`: na criação não aparece, porque todo registro nasce ativo. Os períodos financeiros ficam de fora: a situação deles é o status (aberto ou encerrado), que o formulário não edita. Os textos são "Inativar para remover das listagens" (cadastros) e "Inativar para impedir o login" (usuários). O rodapé do `FormCard` não tem `border-t`, para não duplicar a borda do último bloco.
- `CurrencyDisplay` mostra `R$ 0,00` para o zero (a v4 não mostrava nada); `null` só mostra algo com `zeroIfNull`. Sai sempre em `font-mono tabular-nums`. Com `signed`, o valor ganha `+ ` ou `− ` (U+2212) e a cor de receita (`text-income`) ou de despesa (`text-expense`); o zero fica sem sinal e sem cor. Use `signed` onde o valor é movimento de dinheiro: a cor sozinha nunca basta. `bare` tira o "R$" (para a coluna cujo cabeçalho já diz "(R$)"), `glued` cola o sinal ao valor ("−1.850,00", "+R$ 8.400,00"), `neutral` tira a cor, `sign` (`income` ou `expense`) força o sinal e a cor mesmo no zero, para os cartões que sempre mostram "+R$ 0,00" ou "−R$ 0,00" (o valor aparece sem sinal próprio: passe o absoluto ou deixe o componente tirar o sinal) e `tone` (`'income'` ou `'expense'`) só colore, sem sinal: serve onde a cor diz se é crédito ou débito e o valor é um total positivo (o `signed` vence o `tone`).
- `StatusBadge` usa o `Badge` neutro (inativo com `opacity-70`) e, com `feminine`, diz "Ativa" e "Inativa" (`status.feminine.*`): carteiras e classificações passam `feminine-status` ao `ItemsTable` e ao `DetailCard`, como as abas já diziam "Ativas"/"Inativas"; cartões e centros de custo ficam no masculino. O `PeriodStatusBadge` recebe o `status` do período (`OPEN` ou `CLOSED`) e o `expired` (calculado pelo server, nunca gravado): "Aberto" (`approved`), "Aberto · expirado" (`highlight`, com o relógio e sem o ponto) e "Encerrado" (`neutral`, com o cadeado). Um período expirado continua aceitando lançamentos; a lista o marca com o marca-texto na linha e um aviso no topo. Só o período aberto se edita, e nenhum se exclui pela tela: o menu "…" da lista tem Fechar período e Editar nome e metas no aberto e Reabrir no encerrado, e o `DetailCard` recebe `readonly` (sem Excluir e Editar). O detalhe do período mostra o resultado provisório, de `GET /financial/financial-periods/{id}/result`.

### Layout e rotas

O `App.vue` só tem o `<RouterView>`, o `Toaster` e o `ConfirmDialog`. As seções (`DASHBOARDS`, `FINANCIAL`, `REGISTRATION` e `ADMINISTRATION`, nessa ordem) estão num registro só, `components/layout/sections.ts`: `path`, `label` do i18n, `role` e os `items` (`label`, `icon` do Lucide e `to`). A `TopBar` e o `MobileMenu` leem esse registro, e cada layout de seção monta a `PageStructure` e passa a sua seção ao menu lateral pelo slot `side-menu`. Um item sem `to` aparece desabilitado: é o que boa parte do financeiro e as integrações da configuração têm hoje. Um item com `group` (a chave do i18n do rótulo) abre um grupo novo no menu lateral, que o `SideMenu` desenha com o rótulo do grupo no lugar do da seção (o Financeiro tem os grupos "Dia a dia" e "Período"); o menu do celular (`MobileMenu`) passa `flat` e mostra só o rótulo da seção. O item de menu `exact: true` só fica ativo no caminho exato (a Visão geral, `/dashboards`, senão ficaria ativa em todos os dashboards).

**O shell:** toda tela privada tem o menu lateral (a `PageStructure` não tem prop para desligá-lo). A `TopBar` mostra o botão do menu (`Ctrl+B`), as seções que o usuário pode ver (a atual com o sublinhado verde e `aria-current`) e o `UserMenu` (nome e e-mail, tema em Claro, Escuro e Sistema, idioma em `pt-BR` e `en-US`, dispositivos confiáveis e Sair). Clicar numa seção do topo troca o menu lateral por inteiro e abre a capa dela. O menu lateral tem a marca no topo (leva a `/`), os itens da seção (o atual em negrito com o `marker`) e a versão do app (`APP_VERSION_LABEL`, de `utils/appVersion.ts`: `v<versão>` ou `dev` sem a variável `VITE_APP_VERSION`) no rodapé; aberto tem 240px e, recolhido, vira uma faixa de 52px de ícones com tooltip, e o estado fica no cookie `sidebar_state` do `SidebarProvider`, lido a cada `PageStructure` para valer entre seções. Abaixo de 768px o menu lateral é um Sheet com todas as seções permitidas e, no rodapé, o usuário, o idioma, o tema e o Sair; a marca da barra só aparece no celular. O item Dispositivos confiáveis do menu do usuário (no celular, o botão ao lado do tema, no rodapé da folha) abre o `TrustedDevicesDialog` (veja [Dispositivos confiáveis](#dispositivos-confiáveis)). A versão do app só aparece no menu lateral do desktop.

**A raiz `/` (rota `start`) não tem tela.** O registro dela, em `router/index.ts`, existe só para a raiz não cair na rota coringa pública; quem a redireciona é o `authGuard`, depois de restaurar a sessão e de checar a aprovação: o usuário vai para a primeira seção que pode acessar, na ordem de `sections` (`DASHBOARDS`, `FINANCIAL`, `REGISTRATION`, `ADMINISTRATION`), e quem não tem nenhuma role de seção vai para a `403`. Não use `redirect` no registro: ele resolve antes dos guards, quando a sessão ainda não foi restaurada. O destino padrão do login, do "Ir para home" e da marca é essa rota (`{ name: 'start' }` ou `/`).

**Capas dos módulos.** Financeiro, Cadastros e Configurações abrem uma capa (`views/<módulo>/<Módulo>HomeView.vue`, que só monta o `ModuleHome`): o cabeçalho do módulo e uma grade (`grid-cols-[repeat(auto-fill,minmax(320px,1fr))]`) com um cartão por item do menu lateral: ícone em quadrado `bg-accent`, nome, uma frase (`module-home.items.*`, a chave vem do `description` do item em `sections.ts`) e, à direita, a contagem em mono. A contagem é o `count('ALL')` do store de cada cadastro (e dos usuários), sem filtro, carregada ao montar pelo `useModuleCounts`; se a chamada falha o cartão aparece sem ela (o `count` já devolve `null` e marca o erro como tratado, então não há toast). Um item sem `to` vira um cartão apagado (`aria-disabled`, `opacity-60`), não clicável, com o selo "Em breve". Um item novo no `sections.ts` ganha a frase no `pt_BR.json` e o cartão aparece sozinho.

**Dashboards.** Os cinco itens (`/dashboards`, `/mes-atual`, `/meses-anteriores`, `/por-carteira` e `/por-classificacao`) usam a mesma `DashboardView`, que recebe o título e a descrição como props da rota (`props: { title, description }`, chaves do i18n) e mostra só o estado vazio "Os dashboards chegam com o financeiro": nada de números ou gráficos inventados. Os nomes são de exemplo; os reais e o `chart.js` vêm do épico do financeiro (#34).

As rotas ficam em `src/router/`, um arquivo por seção: `dashboardsRoutes.ts`, `registrationRoutes.ts`, `financialRoutes.ts`, `configurationRoutes.ts` e `publicRoutes.ts`, montados no `index.ts`. Cada seção é um registro com o layout como `component` e as telas como `children` carregadas sob demanda (`() => import(...)`); uma tela nova entra como filha do registro da sua seção. Três chaves de `meta` valem (os tipos estão em `router/routeMeta.ts`):

- `public: true` no registro do layout marca a rota como pública (o `isPublicRoute` olha todos os registros de `to.matched`). São públicos o `/login`, o `/auth/*` e as telas de erro (veja [Telas de autenticação e de erro](#telas-de-autenticação-e-de-erro)).
- `breadcrumb` guarda a chave do i18n que o `PageBreadcrumb` mostra; repetir a mesma chave num filho não duplica o item. O último item é a página atual. No celular a trilha aparece inteira ("Financeiro › Fatura do cartão › Detalhando"), como no mock. O `PageBreadcrumb` é sempre o primeiro filho da área de conteúdo da `PageStructure`, no canto superior esquerdo, e fica a 12px (`mb-3`) do cabeçalho em todas as telas; as views não somam margem de topo por cima.
- `role` no registro do layout de uma seção exige essa role do usuário em toda rota dela: `/dashboards` pede `DASHBOARDS`, `/registration` pede `REGISTRATION`, `/financial` pede `FINANCIAL` e `/configuration` pede `ADMINISTRATION`. A raiz e as rotas públicas não pedem nenhuma. Uma seção nova ganha a `role` da sua área no registro do layout e uma entrada em `sections.ts`.

O guard (`router/guard.ts`): rota pública passa; senão, com sessão no store ou com `restoreSession()` verdadeiro segue; senão vai para `{ name: 'login', query: { redirect } }`. Com sessão, se algum registro de `to.matched` pede uma role que o usuário não tem (`auth.hasRole`), vai para `{ name: '403' }`, a tela `/error/forbidden`. A raiz (`start`) é a exceção descrita acima. **Isso é UX, não controle de acesso:** o server confere a role em cada requisição, e a `TopBar` só esconde as seções sem a role pelo mesmo motivo. Os testes que chamam o `router/index.ts` precisam de um `createTestingPinia` ativo, e cada rota carregada sob demanda é coberta por um teste que resolve todos os carregadores (`router/index.test.ts`), então uma rota nova entra na contagem dele.

**O `redirect` é entrada do usuário.** Quem o usa depois do login passa por `safeRedirect` (`utils/safeRedirect.ts`), que aceita só caminho interno (começando em `/`, sem `//` nem `/\`) e devolve `null` para o resto; o `LoginView` cai na raiz (`start`) nesse caso.

### Notificações e confirmações

`useNotification()` (sobre o `vue-sonner`) devolve `showSuccess`, `showInfo`, `showWarn` e `showError` com a assinatura da v4 (`título, detalhe, localizar = true`, as duas strings como chaves do i18n) e o `showApiNotice`, que mostra o que o `describeApiError` descreveu. O `Toaster` fica no `App.vue`, e o CSS do `vue-sonner` é importado no `main.ts`.

O `plugins/apiErrorHandler.ts`, instalado no `main.ts`, mostra o toast de todo `ApiError` que o `describeApiError` descreve (adiado por um `setTimeout(0)`: um erro que uma tela já tratou, marcado com `markHandled` pelo `useServerErrors().run()`, não vira toast; veja [Cadastros](#cadastros)) e cuida da sessão. No 401: `invalid-credentials`, `account-disabled` e `invalid_totp_code` são das etapas do login e passam; com sessão no store (`unauthenticated`, `session-revoked`) chama `auth.expireSession('expired')`; sem sessão limpa o store e, se a tela atual não for pública, leva ao `/login?redirect=`. Os 429 `too_many_login_attempts`, `too_many_registration_attempts` e `too_many_totp_attempts` são das etapas do login e passam (um 429 de outro código segue no toast). No 403 `forbidden` (a role foi tirada no meio da sessão) leva ao `403`; o 403 `pending_approval` leva ao `/pending-approval` (sem navegar de novo se já está lá) e o `invalid-csrf-token` vira o toast "Requisição não autorizada". Uma chamada `silent` não passa por nada disso.

`useConfirmDialog()` devolve o `confirm(opções)`, o `confirmRemoval(entidade, nome)` (a pergunta de remover dos cadastros, com os textos de `<entidade>.remove.*`), o `confirmDiscard(nome)` ("Sair sem salvar?") e o `confirmDelete()`, que abrem o `ConfirmDialog` (um `alert-dialog` montado uma vez no `App.vue`) e resolvem uma promessa com `true` ou `false`. Sem opções, o texto é o de exclusão da v4:

```ts
if (await confirmDelete()) {
  await wallets.remove(id)
}
```

### Formulários

Todo formulário usa o `useForm` do vee-validate com um esquema Zod, e os campos usam os componentes de `components/ui/form` (`FormField`, `FormItem`, `FormLabel`, `FormControl`, `FormMessage`). O esquema fica em `src/schemas/<formulario>Schema.ts`, um arquivo por formulário, e é embrulhado com o `toTypedSchema` local de `schemas/typedSchema.ts` (veja `loginSchema.ts`). As mensagens de validação não ficam no esquema: o `schemas/zodErrorMap.ts`, instalado no `main.ts`, as traduz pelas chaves `validation.*` do i18n, então `z.string().min(1)` já dá "Campo obrigatório". O mapa conhece obrigatório, tamanho mínimo e máximo de texto, mínimo e máximo de número, email e uma regra cruzada própria (issue `custom` com `params: { i18n }`, que vira a chave `validation.<i18n>`, como o `end-before-start` do período financeiro e o `password-mismatch` da recuperação de senha); uma regra nova vira uma chave em `validation` e um caso no mapa. O `zod` está na linha 4. O `toTypedSchema` é local porque o `vee-validate` 4.x não aceita Standard Schema (só o 5, ainda em beta) e o `@vee-validate/zod` pede `zod ^3.24`; quando o `vee-validate` for para o 5, o adaptador sai e os schemas vão direto ao `useForm`. O mapa usa a API do Zod 4 (`z.config({ customError })`, `invalid_format`, `issue.origin`), e devolver `undefined` mantém a mensagem padrão do Zod, em inglês.

### Cadastros

Carteiras, cartões, centros de custo e classificações vivem em `src/views/registration/<recurso>/` (os períodos financeiros, em `src/views/financial/periods/`, sob `/financial/periods`, porque são uma operação do dia a dia do Financeiro), três telas cada: `<Entidade>ListView`, `<Entidade>FormView` (criar e editar) e `<Entidade>DetailView`. As rotas saem do `router/crudRoutes.ts`, que monta, dentro do registro da seção, o registro do recurso (só com a migalha `<entidade>.menu`) e a filha de caminho vazio (a lista, nome `wallets`), `create`, `:id/update` e `:id/detail` (nomes `wallets.create`, `wallets.update`, `wallets.detail`), com `props: true`: o `id` chega como prop e é ele que diferencia o formulário de edição do de criação. **A v4 tinha uma quinta rota, `:id/delete`, que mostrava o detalhe com a pergunta "Confirma a exclusão?". Ela não existe mais:** a exclusão, na lista e no detalhe, passa pelo `useConfirmDialog().confirmDelete()`.

**O padrão de listagem, formulário e detalhe (#76, mockup na #73).** Toda tela de cadastro, e a de usuários (#78), segue o mesmo desenho; para uma tela nova, copie uma das cinco. O `entity` que as telas passam aos composables é o prefixo do i18n da entidade (`wallet`, `cost-center`, `users`), e as chaves que ele pede são sempre as mesmas: `<entidade>.list.{description,empty-title,empty-description,plural,found}` (o `found` é a frase do rodapé com busca, no singular e no plural separados por `|`, com `{count}` e `{query}`), `<entidade>.remove.{title,description}` (com `{name}`), `<entidade>.toast.{created,updated,removed}` e `...-detail` (com `{name}`), `<entidade>.sections.*` e `<entidade>.form.{create,active-label,active-hint}`.

- **Lista:** `PageContainer` > `PageHeader` (título, descrição e o botão "Criar", o mesmo rótulo do envio do formulário de criação, nas `actions`) > `SearchControls` > `ServerErrorAlert` (só para erro de remoção) > `ListState` ou `ItemsTable`. O `useCrudList` recebe `routeName`, `entity`, `initialStatus`, o `pageRequest`, o `pageResponse`, o `loading`, o `findAll` e o `remove` do store (o `count` do store e a lista `statuses` das abas são obrigatórios: toda lista mostra as contagens) e devolve o `searchSummary` (a frase `<entidade>.list.found` com o texto que a última carga usou, ou `undefined` sem busca; vai na prop `summary` do `ItemsTable`) e os manipuladores de busca (`search` volta à primeira página), `clearSearch`, paginação, ordenação, navegação e `remove(linha)`; carrega a lista no `onMounted`. As contagens de cada aba vêm de uma consulta de `size: 1` por situação (o `count` do `useCrudResource`, sem texto de busca, sem o `loading` e sem toast), feita ao abrir a tela e depois de remover. `listState` diz o que mostrar: `error` (a carga falhou; o alerta do topo não repete esse erro), `empty` (nenhum registro e nada filtrado; usa a contagem de Todos, e cai no filtro quando a contagem não veio), `no-result` (busca ou situação sem resultado) ou `table`; `busy` é o esqueleto (`loading` do store ou primeira carga ainda em curso, para o vazio não piscar). A lista passa `detail-route`, `:current-page`, `:page-size`, `:sorted-field` e `:sorted-order` do `pageRequest` ao `ItemsTable`, e `sortFields` ao `useCrudList`; o estado da lista vive na URL (veja [Filtros na URL](#filtros-na-url)).
- **Formulário:** `FormCard` (título, descrição, alerta do topo, seções e rodapé) com um `FormSection` por seção (na edição, o primeiro bloco é o `StatusSection` da situação, que vem antes de todas; título e ajuda à esquerda, campos à direita em `md:grid-cols-[220px_…]`, uma coluna no celular; `conditional` pinta o fundo das seções que aparecem e somem). O rodapé tem Cancelar e o botão de salvar (`submit-label`: "Criar" ao criar, "Salvar" ao editar, sem o nome do formulário; "Salvando…" durante o envio), fica preso no fim da tela (`sticky`) e mostra "Alterações não salvas" quando o formulário sujou. Enquanto carrega o registro (`loadingRecord`, não o `loading` do store, que a busca do seletor também acende) ou envia, o `<fieldset>` desabilita os campos. `useForm` do vee-validate com o esquema de `src/schemas/<entidade>Schema.ts`, que também exporta os valores iniciais e as funções `to<Entidade>CreateForm`, `to<Entidade>UpdateForm` e `to<Entidade>FormValues` (esquema de formulário e payload da API não são iguais: `''` vira `null`, a opção escolhida vira o `id`). O `useCrudForm` carrega a entidade quando há `id` (o formulário carregado é a base: não conta como alteração), grava e mostra o toast. **Criar em sequência (#247):** depois de criar, a tela fica no formulário de criação, limpo (`resetForm()` com os valores padrão da tela), com o foco no primeiro campo e o toast `<entidade>.toast.created`, sem navegar para o detalhe; o guarda de descarte não dispara, porque o formulário limpo não está sujo. Quem cadastra vários registros em sequência não volta ao formulário a cada um. Uma tela de criação própria, fora do `useCrudForm`, segue a mesma regra. Depois de **editar**, a tela vai para o detalhe quando passa `detailAfterUpdate` (as telas de cadastro) e, sem ele (usuários), fica na tela com o formulário recarregado com os valores gravados. Sair com alterações (Cancelar, o menu ou o voltar do navegador) abre a confirmação "Sair sem salvar?" por um `router.beforeEach` que o composable instala e tira ao desmontar (rotas públicas passam sem pergunta, para o fim de sessão e o 403 não ficarem presos no diálogo; recarregar ou fechar a aba não é guardado). Os campos são `InputField` (texto, número, data e `multiline`), `MoneyField`, `SelectField` e `SearchSelectField`; `required` põe o "*" no rótulo e `mono` usa a fonte de valores (agência, conta, números). **Campo condicional some (`v-if`), não fica desabilitado**, e o `to<Entidade>…Form` o manda `null` (como o `hasBankData` faz). Número e data usam o `<input>` nativo (a data já sai como `yyyy-mm-dd`, o formato da API, sem passar pelo UTC, e o calendário abre quando o campo recebe o foco); todo valor em reais usa o `MoneyField` (`components/forms/MoneyField.vue`, a regra de leitura está em `utils/money.ts`): o campo mostra `R$ 12.345,67` enquanto se digita, só os dígitos contam e entram como centavos (digitar `1234567` dá `12345.67`), e o valor no formulário é um número ou `null`, que é o que o server recebe; o `optionalNumberSchema` converte o texto em número ou `null`.
- **Validação:** o `InputField` valida ao sair do campo e, depois do primeiro erro, a cada mudança (`validate-on-model-update` desligado e `handleChange(valor, errors.length > 0)`); o `SelectField` valida ao escolher (com `none-label` ganha uma primeira opção que limpa o campo, `null`, como a carteira sugerida do cartão). Ao enviar com erro, o foco vai para o primeiro `[aria-invalid="true"]` do formulário. O texto abaixo do campo é só da validação do próprio campo.
- **Cancelar não tira o foco do campo (#291):** o botão Cancelar do `FormCard` e o de todo diálogo com campos (`@mousedown.prevent`) não deixam o `mousedown` roubar o foco. Sem isso, o `blur` roda a validação, a mensagem aparece, o rodapé desce e o `mouseup` cai fora do botão: o `click` não dispara e o primeiro clique é perdido. O teclado (Tab até o botão e Enter) e a guarda de "Alterações não salvas" não mudam. Um diálogo novo com campos faz o mesmo no Cancelar.
- **`SearchSelectField`:** o seletor com busca no servidor (carteira do cartão, centro de custo pai). Só busca com dois caracteres ou mais, emite `search` com o texto e mostra as `options` que a tela passa; o valor do campo é `{ id, label }` ou `null`. O centro de custo pai aparece pelo `fullName`.
- **Detalhe:** `DetailCard` (nome como título, a `badge` de situação ao lado, Excluir em contorno e Editar no cabeçalho, alerta do topo) com um `DetailSection` por seção, as mesmas do formulário, e `DetailField`s (`mono` e `wide`); o `useCrudDetail` carrega, leva à edição e remove com confirmação. Não há botão Voltar: o caminho de volta é o breadcrumb.
- **A tela segue o mock aprovado exatamente.** Uma divergência do mock é decisão do usuário, nunca da implementação; o que o mock pede e o server ainda não entrega vira issue de server, não um recurso cortado da tela.
- **Textos de tela:** o botão de criação das listas e dos estados vazios é sempre "Criar", nunca "Novo X"; o breadcrumb é um verbo da ação em curso ("Editando", não "Editar") e, no detalhe e na edição, termina no verbo ("Cadastros › Centros de custo › Detalhando"): o nome do registro aparece no cabeçalho logo abaixo e não se repete na migalha. As chaves `<entidade>.form.new`, `.editing` e `.detailing` guardam só esse verbo ("Criando", "Editando", "Detalhando"; en "Creating", "Editing", "Viewing") e são as que o `crudRoutes` e as rotas do financeiro e dos usuários usam; o título do formulário lê chaves próprias (`form.title-new` e `form.title-editing`, "Nova carteira" e "Editar carteira"), nunca a da migalha; o campo de busca sempre mostra os campos que pesquisa; a paginação mantém primeira, anterior, página, próxima, última e o seletor de linhas. Se um mock divergir disso, vale esta regra.
- **Ordenação.** Toda listagem abre ordenada pela data de criação, do mais recente para o mais antigo (`createdOn,desc`, definido no `createPageRequest`; um store novo não passa `sortField` nem `direction`), e a coluna de nome é sempre ordenável (`sortable: true`; nos centros de custo é o `fullName`, o nome com a hierarquia). Os três cliques no cabeçalho do nome vão de crescente a decrescente e de volta ao padrão. **Uma lista sem nome não tem essa alternativa óbvia: pare e decida com o usuário qual coluna a substitui.** **No financeiro, cada tela abre na ordem do mock:** movimentos pelo vencimento crescente, períodos pelo início decrescente, extrato e transferências pela data decrescente, faturas pelo nome do cartão, recorrentes pelo nome; os cadastros continuam pela data de criação decrescente, exceto os centros de custo, que abrem pelo nome completo crescente (`fullName,asc`: `createPageRequest({ sortField: 'fullName', direction: 'asc' })` no store, mais `defaultSort` no `useCrudList` e `default-sort-field` no `ItemsTable`, para a ordem padrão não ir para a URL). O client manda o `sort` da tela; o padrão do server não muda.
- **Verificação no navegador.** Antes de abrir o PR de uma tela, compare-a com o mock no navegador, no desktop e a 390px, nos temas claro e escuro, e descreva a conferência no corpo do PR. Use um ambiente descartável, nunca as portas 8085 e 8086 do usuário: o server por `./gradlew bootTestRun --args='--server.port=18085'` em `server/` (o Postgres vem do Testcontainers) e o Vite por `pnpm dev --port 18086`, com o proxy de `/private` do `vite.config.ts` trocado localmente para a 18085 (sem commitar). No fim, derrube os dois, matando a JVM pelo PID.
- **Excluir** (o texto do botão e do menu, `crud.actions.remove`; o código continua `remove`) sempre pede confirmação (`useConfirmDialog().confirmRemoval(entity, nome)`) com o nome do registro e o que acontece com os dados ligados (`<entidade>.remove.description`), e o sucesso vira toast ("Carteira excluída", com o nome).
- **Erro do servidor:** o `useServerErrors().run()` envolve toda chamada da tela; se ela falha, as mensagens (as mesmas do `describeApiError`) vão para o `ServerErrorAlert`, no formulário, no detalhe ou acima da tabela, **e não viram toast**: o `run()` marca o erro com `markHandled` (`utils/handledErrors.ts`) e o `apiErrorHandler`, que só mostra o toast num `setTimeout(0)`, pula o que estiver marcado (a navegação de 401 e 403 continua imediata). Quando o erro é sobre um campo (o 409 traz `parameters['wallet.name']`, `card.last-four-digits`…), o `run()` também preenche `fields` (`name`, `lastFourDigits`…); o `FormCard` os repassa por `provide` e o `FormControl` (em `ui/form`) marca o campo com a borda vermelha e o `aria-describedby` do alerta (`SERVER_ERROR_ALERT_ID`), sem repetir o texto embaixo; a marca sai quando o formulário muda. Chamada fora de uma tela de cadastro continua com o toast.
- **Testes:** cada tela tem um `*.test.ts` com `createTestingPinia({ stubActions: false })` (via `mountView` de `src/test/crud.ts`) e o módulo `@/api/<recurso>` mockado, para exercitar o store de verdade. A confirmação (remover ou sair sem salvar) se resolve com `useConfirmDialog().accept()` ou `.cancel()`, sem montar o `ConfirmDialog`. Depois de um `submit`, use o `settle()` do mesmo helper: a validação do vee-validate é assíncrona. Os outros helpers de `src/test/crud.ts`: `chooseRowAction(wrapper, linha, 'Remover')` abre o menu "…" da linha (o menu do Reka abre com `keydown` Enter) e escolhe a ação; `serveListing(findAll, linhas, total, contagens)` atende a listagem e as consultas de contagem (`size: 1`) de uma vez; `listingCalls` devolve só as chamadas da listagem; `stateOf` diz qual `ListState` aparece; `useCompactViewport(true)` simula o celular (volte com `false` no `afterEach`). `buttonWithText` ignora o número da contagem no fim do texto das abas.

### Filtros na URL

**Toda tela com filtros guarda o estado na URL**, para que um link compartilhado abra exatamente a mesma tela e recarregar não perca nada (como no investlog). Vale para as seis listas (carteiras, cartões, centros de custo, classificações, períodos e usuários) e para toda tela com filtro que vier: filtro, situação, página e ordenação nunca ficam só em estado de componente ou de store.

O estado vive em cinco parâmetros da query: `filter` (o texto de busca), `status` (a aba de situação), `page` (a página, **começando em 1**; o `pageRequest.current` é zero-based), `size` (o tamanho da página, um de `PAGE_SIZE_OPTIONS`) e `sort` (`campo,asc|desc`). **O que é o padrão não vai para a URL**: primeira página, 15 por página, `createdOn,desc`, texto vazio e a aba inicial (`initialStatus`). A lista sem parâmetro nenhum é a lista padrão.

- **`utils/listQuery.ts`** é a parte pura: `parseListQuery` lê a query e valida cada valor (situação fora das abas, página que não é inteiro positivo, tamanho fora de `PAGE_SIZE_OPTIONS`, campo de ordenação fora de `sortFields` ou direção que não é `asc` nem `desc` caem no padrão, sem erro e sem quebrar a tela), e `buildListQuery` escreve o estado, preservando os parâmetros que não são da lista (como o `from` de um link de e-mail) e tirando os do padrão.
- **`composables/useListFilters.ts`** liga isso à rota. Ao ser chamado, **a URL sobrescreve o `pageRequest`**: o store sobrevive entre telas, mas quem abre a lista vê o que a URL diz, nunca o que sobrou da visita anterior. `writeRoute()` grava o estado com `router.replace` (nunca `push`, para não empilhar histórico) e não navega quando a URL já diz o mesmo. Quando a URL muda por fora com a lista aberta (um link colado, o link do e-mail, o voltar do navegador) e o que ela diz é diferente do estado, o estado a segue (só enquanto a rota ainda é a da lista: sair para o formulário não zera o estado nem recarrega) e o `onExternalChange` recarrega; a mudança que a própria lista acabou de gravar é reconhecida por dizer o mesmo que o estado e não recarrega de novo.
- **O `useCrudList` já usa os dois**: recebe `sortFields` (os campos que a lista aceita ordenar, os `sortable` das colunas mais `active` quando a coluna Situação existe; sem a lista, uma URL poderia mandar o server ordenar por um campo que ele recusa) e grava a URL no início de cada `reload()`, que é por onde passam busca, aba, página, tamanho e ordenação. Uma lista nova de cadastro não escreve nada de URL: passa `sortFields` e liga `:sorted-field="pageRequest.sortField"` e `:sorted-order="pageRequest.direction"` no `ItemsTable`, que assim mostra a ordenação que veio da URL (sem essas props ele só guarda a ordenação do último clique).
- **Parâmetros extras.** Uma lista com filtros além dos cinco (os movimentos têm `period`, `type`, `costCenter`, `classification` e `overdue`) passa `extra` ao `useCrudList`/`useListFilters`: `keys` (os nomes na query), `values` (um `Ref<Record<string, string>>`, no store, que o `findAll` lê) e, se for o caso, `sanitize`, que descarta o valor inválido. Os extras seguem a mesma regra dos cinco: preenchidos vão para a URL, vazios saem dela, e uma mudança de fora recarrega a lista. Os nomes dos parâmetros são os do client (em inglês), nunca os do mock.
- **Uma tela de filtros que não é lista de cadastro** usa o `useListFilters` direto com o seu `pageRequest`, ou, se os parâmetros forem outros, o mesmo desenho (ler com validação, gravar com `replace`, seguir a URL), e entra nesta regra.

### Movimentos

Telas em `src/views/financial/movements/` (`MovementListView`, `MovementFormView` e `MovementDetailView`), sob `/financial/movements` (nomes `movements`, `movements.create`, `movements.update` e `movements.detail`; o `crudRoutes` aceita `form` omitido, e então não registra `create` nem `update`). O desenho é o do mockup da #161 (lista com faixa de totais, filtros em linha e detalhe com avisos), com as diferenças do server:

- **O período abre sozinho.** Sem `period` na URL, a lista carrega os períodos (`useMovementFilterOptions`, que também traz centros de custo e classificações para os filtros) e abre no período aberto que contém hoje (`defaultPeriod` de `utils/movements.ts`; senão o aberto mais recente) e o grava na URL com `replace`; `period=all` é "todos os períodos". Os quatro cartões de resumo (Recebido, Pago, Resultado e A pagar, com o selo "N vencidos" ou "Nada vencido") vêm de `GET /financial/financial-periods/{id}/result` (`revenues`, `expenses`, `result`, `toPay` e `overdueExpenses`) e só aparecem com um período escolhido; são 4 colunas no desktop e 2 no celular, com o sinal colado ao valor (`CurrencyDisplay signed glued`).

As contagens das abas seguem a busca e os filtros (`countsFollowFilters` do `useCrudList`). O rodapé diz "1–15 de 33 movimentos" (`noun` do `ItemsTable`). - **Situação.** `MovementStatusBadge`: "Em aberto", "Pago" e "Vencido há N dias" (marca-texto, `pending`, só o relógio); a linha vencida leva o marca-texto (`marked-row`). `overdue` vem calculado do server. Pago: sem botões no cabeçalho e rodapé com "Ver no extrato" e "Desfazer pagamento". Desconto zero aparece como "---" e o valor sai sem sinal. ### Carteiras, extrato e ajuste de saldo

A lista de carteiras (`views/registration/wallets/WalletListView.vue`) segue o design: busca e abas num cartão só, colunas Nome, Tipo, Banco, Agência / conta e Saldo atual (R$) (o saldo sai sem "R$", com o negativo em vermelho e o sinal colado; só Nome, Tipo e Saldo ordenam), menu "…" com Ver extrato, Ajustar saldo, Editar e Excluir (o `WalletRowActions`) e o ajuste aberto na própria lista. A busca procura em nome, banco, agência e número. O detalhe traz o aviso "O saldo não se edita na carteira" (o slot `notice` do `DetailCard`, entre o cabeçalho e o cartão), as seções Identificação, Dados do banco (Banco, Agência e Conta) e Saldo (saldo atual e "Última movimentação") e o rodapé com Ver extrato, Transferir e Ajustar saldo; não mostra Descrição.

O extrato (`views/financial/statement/StatementView.vue`, rota `/financial/statement`, nome `statement`) lista as mudanças de saldo de **uma carteira** (`GET /financial/wallets/{id}/statement`, `api/walletEntries.ts`, store `statement`). **Sem `wallet` na URL abre na carteira ativa cuja última linha de extrato é a mais recente (`lastEntryOn` da `WalletListView`); sem lançamentos em nenhuma, na primeira ativa em ordem alfabética** (`defaultStatementWallet`, em `utils/statement.ts`), e a grava com `replace`; sem carteira nenhuma mostra o estado vazio e não carrega nada.

- **Cabeçalho e cartões.** As ações são "Ajustar saldo" e depois "Transferir". Quatro cartões: a carteira (seletor e "Conta bancária, Banco do Brasil"), "Saldo atual" com "Atualizado em dd/mm/aaaa hh:mm", "Créditos no filtro" (total em verde, `tone="income"`) e "Débitos no filtro" (total em vermelho, `tone="expense"`), os dois sem sinal e com "N linhas"; o saldo atual só ganha "−" e o vermelho quando é negativo. Os totais vêm de `GET /financial/wallets/{id}/statement/summary` (`store.findSummary`, com os mesmos filtros da lista, sem página nem ordem); o saldo e a data de atualização vêm de `GET /registration/wallets/{id}` e da própria resposta do resumo.
- **Filtros na URL** (parâmetros extras do `useListFilters`, `STATEMENT_FILTER_KEYS`): `wallet`, `period`, `origin`, `from`, `to`, `min` e `max`, mais `filter` (nome do lançamento), `status` (Todos, Créditos ou Débitos, que viram `direction`), `page`, `size` e `sort`. Operação desconhecida e valor que não é número caem no padrão. `toStatementQuery` traduz o estado para a consulta do server e `toStatementFilter` (a mesma, sem paginação) para o resumo. Busca, abas e filtros ficam num cartão só, e os valores mínimo e máximo usam o `MoneyFilter` (`components/forms/`, com o addon "R$" e o texto "0,00").
- **Tabela:** data e hora, operação (o `OperationBadge`, com ícone e cor por tipo), lançamento, valor (ícone de entrada ou saída e a cor da direção, sem sinal e sem "R$"), saldo anterior e saldo atual (sem "R$"; só o negativo leva "−" colado e o vermelho), e uma última coluna sem título visível ("Abrir origem", só para leitor de tela) com a seta ↗. O lançamento de uma transferência diz "Para X", "De X", "Devolução para X" ou "Devolução de X" (`entryLabel`, pelo `returnTransfer` da referência) e o de um estorno, "Estorno de X". A linha de estorno ganha o marca-texto. **Clicar na linha abre o detalhe do que a originou:** o movimento (`/financial/movements/{id}/detail`), a transferência (`/financial/transfers/{id}/detail`) ou, sem origem (ajuste), o detalhe do próprio lançamento (`StatementEntryView`, rota `statement.detail`, `GET /financial/wallets/{id}/statement/{entryId}`). A linha de uma transferência que ainda pode ser devolvida (`returnable`) tem o botão "Devolver", que abre o `GiveBackDialog`. A ordem padrão é a data e hora decrescente, e a coluna ordenada mostra o ícone mesmo na ordem padrão (`active-sort-icon-only` do `ItemsTable`).
- **Estados.** Vazio ("Conta corrente ainda não tem lançamentos", com "Criar", que vai ao formulário de movimento), sem resultado ("Nenhuma linha no extrato com esses filtros") e erro ("Não foi possível carregar o extrato"), todos pelo `copy` do `ListState`.
- **Ajuste de saldo.** O `AdjustBalanceDialog` (`components/wallets/`) pede só o valor, com sinal (`MoneyField signed`: "+0,03 ou −0,02", digitar `-` ou `+` troca o sinal; zero é recusado pela regra `adjustment-not-zero` do `zodErrorMap`), e mostra o resumo "Saldo da carteira, Ajuste, Saldo depois". Não pede motivo (o server grava "Ajuste de saldo"). Abre pelo extrato, pela lista e pelo detalhe da carteira, só para carteira ativa, e o toast diz "Crédito de 0,03 em Conta corrente. Não entra no resultado." ou "Débito de …" (`adjustmentNotice`).

### Transferências

Telas em `src/views/financial/transfers/` (`TransferListView`, `TransferFormView` e `TransferDetailView`), sob `/financial/transfers` (nomes `transfers`, `transfers.create` e `transfers.detail`; as rotas são escritas à mão em `financialRoutes.ts`, porque não há edição nem exclusão: uma transferência é definitiva). Uma transferência não muda o resultado do período.

- **Lista.** Sem abas de situação: busca (carteira de origem, carteira de destino ou observação) e filtros Carteira (origem ou destino), De e Até e "Limpar" num cartão só, todos na URL (`TRANSFER_FILTER_KEYS` do store, mais `filter`, `page`, `size` e `sort`; ordenável por data e hora, De, Para e Valor). Usa o `useListFilters` direto, como o extrato, porque o `useCrudList` pressupõe abas e remoção. A coluna Situação mostra "Devolvida" (com o ícone ↶) ou "Devolução de dd/mm", ou "—"; a transferência que ainda pode ser devolvida (`returnable`) tem o botão "Devolver" na linha, sem menu "…", e clicar na linha abre o detalhe. No celular o título é "Origem → Destino" (o slot `cell-*` do título recebe `compact`). O estado vazio diz "Nenhuma transferência ainda" e que transferir não muda o resultado. O `useGiveBack` reúne o diálogo, a chamada, o toast e a ida à devolução para a lista, o extrato e o detalhe.
- **Formulário.** Título "Nova transferência" (breadcrumb "Transferindo"). Carteiras (De e Para, só ativas, diferentes entre si pela regra `transfer-same-wallet` do `zodErrorMap`, sem ajuda) e Valor: duas colunas dentro da seção, com os campos (Valor e a Observação opcional, que vai `null` quando vazia, com o texto "Opcional") e o `TransferStatement` ao lado. O extrato da transferência mostra a data de hoje e, por carteira, o saldo anterior, o débito ou crédito e o saldo posterior, recalculado ao digitar com o saldo de `GET /registration/wallets/{id}` (`useActiveWallets().balanceOf`); saldo negativo é aceito. `?from=<carteira>` na URL (os botões "Transferir" do extrato e do detalhe da carteira) pré-seleciona a origem, se ela for uma carteira ativa. Feita a transferência, vai para o detalhe dela. A confirmação de sair sem salvar vem do `useDiscardGuard`, o mesmo que o `useCrudForm` usa.
- **Detalhe.** Só leitura (`DetailCard` com `readonly`), com o nome "Origem → Destino" no título e o selo "Devolvida" ou "Devolução" só quando há devolução. Identificação (data e hora, valor, De, Para e Observação), a seção Devolução só quando a transferência foi devolvida ("Devolvida em dd/mm/aaaa") ou é uma devolução ("Devolve a transferência de dd/mm/aaaa"), com o link para a outra ponta, e o rodapé com "Ver no extrato" e, com `returnable`, "Devolver". O `GiveBackDialog` ("Devolver transferência?") mostra o "Extrato da devolução" (as carteiras trocadas de lado, com a data de hoje) e confirmar vai para a transferência nova. Os `409` `transfer-already-returned` e `transfer-is-a-return` têm mensagem própria: o `describeApiError` usa `error.conflict.<código>` quando o código do conflito tem tradução.
### Cartões e faturas

O cartão é **só de crédito** (#37): não há tipo, o dia do pagamento da fatura (`invoicePaymentDay`, de 1 a 30) é obrigatório e abre em 10, e a carteira que paga a fatura é opcional (vem sugerida ao pagar, e dá para trocar na hora; o select tem a opção "Sem carteira sugerida"). A bandeira é um select (Visa, Mastercard, Elo e American Express, com Visa de partida; uma bandeira antiga em texto livre continua na lista enquanto o cartão a tem). O formulário tem as seções Identificação (nome, bandeira e últimos 4 dígitos, com os exemplos "Ex.: Visa Platinum" e "0000") e Fatura (dia e carteira). Cada cartão ativo ganha uma fatura aberta por período aberto (veja o server), então cadastrar um cartão não pede mais nada do client.

**Cartões** (`views/registration/cards/`). A lista tem o cartão de busca ("Nome, final, bandeira ou carteira", com as contagens das abas acompanhando a busca), as colunas Nome, Final ("••4821"), Bandeira, Dia do pagamento da fatura (ordenável), Carteira que paga a fatura e Situação, e abre pela criação, como todo cadastro. O menu "…" da linha (`CardRowActions`) tem Editar, Ver faturas (a lista de faturas já filtrada pelo cartão), um separador e Excluir. O detalhe não tem botões no cabeçalho: o rodapé traz Ver faturas e Editar, e o cartão só se exclui pelo menu da lista.

**Faturas** (`views/financial/invoices/`, sob `/financial/invoices`, nomes `invoices`, `invoices.detail` e `invoices.import`; não há criar, editar nem excluir, porque a fatura nasce com o período e o cartão). A lista (`InvoiceListView`) usa o `useListFilters` direto, com os extras `period` e `card`, as abas Todas, Abertas, Fechadas e Pagas (`StatusTabs`) com a contagem de cada uma e a ordem padrão pelo nome do cartão (crescente, a do mock; `defaultSort` do `useListFilters` e `default-sort-field` da tabela); o período abre no aberto que contém hoje, como nos movimentos (`period=all` é todos). Os filtros (Período e Cartão, só cartões ativos) e as abas ficam num cartão só. As colunas são Cartão (com o final), Período, Compras, Vencimento ("após fechar" na fatura aberta e a data nas outras), Total (R$) e Situação; a Fechada leva o marca-texto na linha. O `InvoiceStatusBadge` diz "Aberta" (neutro), "Fechada" (marca-texto) e "Paga" (verde). O menu da linha (`InvoiceRowActions`) tem Abrir fatura e, na aberta, Nova compra, Importar fatura e Fechar fatura, e o botão do estado vazio é um "Criar" de contorno que leva ao período novo. O fechar fatura (`useCloseInvoice`, usado pela lista e pelo detalhe) abre o `CloseInvoiceDialog` com "Fechar a fatura de Novembro, Visa Platinum?" (só o mês, `periodMonth`), a quantidade de compras (`purchaseCount`), o pagamento de fatura sem "R$", o vencimento calculado por `utils/invoices.ts` (o mesmo cálculo do server) e a carteira sugerida.

O `InvoiceDetailView` não é um `DetailCard`: o cabeçalho tem o cartão com o final ao lado do nome (slot `title-extra` do `PageHeader`), o período, a situação e as ações (na aberta, Importar fatura, Fechar fatura e Nova compra, a primária por último; nas outras, Ver pagamento de fatura e, na fechada, Excluir pagamento de fatura, que reabre a fatura); abaixo vêm os três números (Total da fatura, Compras e Vencimento, "—" na aberta e dia e mês nas outras), a tabela das compras sem rodapé (Data, Compra, Centro de custo, Classificação e Valor (R$), de `GET /financial/card-purchases?invoice=`, até 500) e, quando há pagamento de fatura, a barra "Pagamento de fatura: nome" com o valor. O `InvoiceView` do server traz o pagamento (`payment`: id, nome e valor), a contagem de compras e o vencimento, então o client não procura mais nos movimentos.

**Importar fatura** (`InvoiceImportView`, `/financial/invoices/import`, breadcrumb "Importando") é só a casca do mock da primeira etapa (Envio, com o cartão, o período, a área de arquivo e o botão, tudo desabilitado, e as "Importações recentes" vazias): o envio, o processamento e o rascunho são da #160. Os três pontos de entrada (a lista, o menu da linha e o detalhe da fatura aberta) já levam a ela, com `?card=` e `?period=`.

**Compra no cartão** (`CardPurchaseFormView` e `CardPurchaseDetailView`, nomes `purchases.create`, `purchases.update` e `purchases.detail`, sob `/financial/invoices/purchases/…`; `purchases` redireciona para a lista de faturas, que é onde o `useCrudForm` e o `useCrudDetail` voltam). O formulário ("Nova compra no cartão", breadcrumb "Lançando compra") tem Cartão e período (o cartão como "Visa Platinum ••4821", já escolhido no primeiro ativo ou no de `?card=`; o período, só os abertos, com "· expirado" nos expirados; travados na edição) e Compra (nome com exemplo, data da compra obrigatória e de hoje, valor, centro de custo e classificação **de despesa**). Sem fatura aberta para o cartão no período, um alerta no topo diz que a fatura está fechada, "Nada foi lançado.", com "Ver a fatura" (ou que não há fatura, quando o cartão não tem nenhuma no período). Lançada a compra, a tela fica no formulário limpo, com o cartão e o período mantidos. O detalhe tem uma seção só (Compra: nome, data, valor, centro de custo, classificação e a fatura "Visa Platinum, Novembro de 2026") e o rodapé Ver fatura e, com a fatura aberta e a compra que não nasceu de um movimento, Editar e Excluir (o mock só mostra Excluir; o Editar fica porque a edição existe desde a #219); quando `movement` vem preenchido, é só leitura, com o aviso e o link para o movimento. O parcelamento (só na criação, a seção Parcelamento com a chave, as parcelas e o valor de cada uma, que dispensa o valor da compra) cria um recorrente no cartão (veja [Recorrentes](#recorrentes)) e a importação fica para a #160. A compra que nasceu de um recorrente traz `recurringMovement` (`id`, `name`, `installment`, `installments`), e o `PurchaseInstallmentBadge` o mostra como no mock: na tabela de compras da fatura, ao lado do nome, o selo `outline` com o ícone de repetir e a parcela ("10/12") ou "recorrente" quando o recorrente não tem prazo (`table`); no detalhe, ao lado do título, só a parcela, sem ícone, e nada para o recorrente sem prazo. O server nomeia o movimento (e a compra) de um recorrente com prazo já com a parcela ("Celular novo 10/12"); o `purchaseDisplayName` (`utils/invoices.ts`) tira esse sufixo do nome mostrado na tabela e no título, para o selo não repetir a parcela como no mock ("Celular novo" mais o selo "10/12").

**Pagar no cartão e pagamento de fatura nos movimentos.** O `PayMovementDialog` da despesa pergunta "Pago por" (segmentado) Carteira ou Cartão de crédito (`via`, com o cartão escolhido entre os ativos do `useActiveCards`, como "Visa Platinum ••4821"): no cartão o payload leva `card` no lugar de `wallet`, o resumo não mostra saldo e traz a linha "Fatura: cartão, mês"; sem fatura aberta, o alerta "Não há fatura aberta de … em …" desabilita o Confirmar. Receita e pagamento de fatura (`invoicePayment`, que o detalhe sabe pelo `invoice` do movimento) só se pagam por carteira. O `MovementStatusBadge` diz "Pago no cartão" (`onCard`) na lista e no detalhe. O movimento com `invoice` é o pagamento de fatura: não tem centro de custo nem classificação (as células mostram "—"), o detalhe não oferece Editar (o server recusa com `invoice-payment-locked`) e põe no lugar o "Ver a fatura"; Excluir só enquanto está em aberto, e reabre a fatura. A despesa paga no cartão leva, no rodapé, o "Ver na fatura" que abre a fatura (`payment.invoice`). A lista tem o filtro "Pagamentos de fatura" (`invoices=true` na URL, `invoicePayments` no server) e o extrato nomeia a operação `INVOICE_PAYMENT`. "Lançar já pago" do formulário de movimento continua só por carteira.

### Fechamento e resultados

**Tela de fechamento** (`views/financial/closing/PeriodClosingView.vue`, `/financial/closing`, nome `closing`, breadcrumb "Financeiro › Fechamento › Fechando": a rota `closing` é um registro com a migalha `period-closing.menu` e a filha de caminho vazio, como as do `crudRoutes`; item "Fechamento" do menu). O período vem de `?period=` (o mock chama de `periodo`; os parâmetros do client são em inglês), gravado com `router.replace` e seguido quando a URL muda por fora; abre no aberto expirado mais antigo e, sem expirado, no que contém hoje (`defaultClosingPeriod` de `utils/periods.ts`), e um `period` que não é de um período aberto cai nesse padrão. O seletor "Período a fechar" fica acima da grade e lista só os períodos abertos ("Outubro de 2026 · expirado"). O store `periodClosing` carrega tudo de uma vez (`GET .../closing`, `.../result`, `GET /financial/period-results/accumulated` e os movimentos `OPEN` do período) e um erro em qualquer chamada vai para o alerta do topo. O `/closing` já traz as faturas do período com a final do cartão, a quantidade de compras e a situação (`invoices`), e o movimento da lista traz `invoicePayment`: não há consulta extra para o selo "fatura" nem para as faturas. O servidor manda `nextOpenPeriod: null` explícito, e a tela lê `== null` mesmo assim. O resumo ("Resumo do período", dois cartões por linha no celular e quatro no desktop) usa o `CurrencyDisplay` com `sign` para forçar o sinal, mesmo no zero: Receitas pagas "+R$ 0,00" em verde, Despesas pagas "−R$ 0,00" em vermelho, Resultado e Acumulado com sinal e sem cor (`neutral`). Pendências: o cabeçalho tem o selo "N restantes" (ou "Resolvidas"), a tabela tem Movimento (o nome é link para o movimento, e a linha inteira abre o detalhe), Vencimento (com o selo "vencido"), Valor (R$) sem o "R$" e "O que fazer", com "Pagar" ou "Receber" e "Mover" com ícones; toda linha leva o marca-texto. Abaixo de 768px as pendências viram cartões (nome e valor, "Vence em 29/10/2026 · vencido" e os dois botões). Sem pendência, o estado vazio traz o ícone, "Nenhuma pendência" e "Tudo o que estava em aberto foi pago ou movido.". Faturas: nome, a final ("••4821"), a linha miúda "4 compras · Aberta", a observação como selo ("Bloqueia o fechamento" com cadeado, "Fecha sozinha com valor zero", "Pagamento de fatura nas pendências", "Paga"), o valor sem "R$" e, na que bloqueia, "Fechar fatura" (`useCloseInvoice`, que reaproveita o `CloseInvoiceDialog`, lê a contagem de compras do próprio `/closing` e busca só o cartão ao abrir); sem fatura, "Nenhum cartão ativo neste período.". A coluna lateral "PARA FECHAR" (letra miúda e maiúscula) tem três itens com a explicação embaixo ("3 faltam pagar ou mover", "1 fatura com lançamento ainda aberta", o nome do período seguinte ou "Não há: pague tudo ou crie um"; o terceiro vale como feito também quando não há pendência) e o botão "Fechar <só o mês>" com a ajuda "Resolva os itens acima." ou "Tudo certo.". Quem manda no botão é o `canClose` do server. Sem período seguinte e com pendências, as pendências abrem com o alerta "Não há período aberto depois de …", com "Criar período" (não há "Pagar tudo": cada pendência tem só o seu botão Pagar ou Receber), e o Mover fica desabilitado ("Não há período aberto depois deste"). Mover (`MoveMovementDialog`, `PATCH /financial/movements/{id}/move`) tem só o título "Mover “nome”" e o campo Período, já no `nextOpenPeriod` (ou no primeiro destino), marca como expirado o destino cujo fim já passou (o `ClosingPeriodView` não traz `expired`) e confirma com "Mover" e a seta. Fechar (`ClosePeriodDialog`, `PATCH .../close`) mostra Receitas "+8.400,00" em verde, Despesas "−5.279,45" em vermelho e o Resultado com sinal, e confirma com "Fechar período" e o cadeado; o toast conta o resultado gravado e as faturas vazias, que o server deixa pagas com valor zero, e a tela vai para a lista de períodos.

**Resultados na lista e no detalhe.** O `FinancialPeriodResultView` ganhou `recorded` (gravado ou provisório). A lista de períodos tem a coluna Resultado: "provisório" no aberto e o valor gravado, com sinal e cor, no encerrado (`GET /financial/financial-periods/{id}/result`, uma consulta por período encerrado da página). O `FinancialPeriodView` e o `FinancialPeriodListView` trazem `reopenable` (só o último encerrado), e o client não procura mais o último encerrado: o store ainda guarda `loadClosedInformation` e `findLastClosedId`, mas a lista e o detalhe não os usam. O fechamento, os menus da lista e o rodapé do detalhe estão em [Períodos](#períodos) e acima.

### Recorrentes

Telas em `src/views/financial/recurring/` (`RecurringMovementListView`, `RecurringMovementFormView` e `RecurringMovementDetailView`), sob `/financial/recurring-movements` (nomes `recurring-movements`, `.create`, `.update` e `.detail`, do `crudRoutes`; o caminho de edição é `:id/update`, como em todos os cadastros). O prefixo do i18n continua `recurrent-movement`, o que o `sections.ts` e as capas já usavam. O recorrente é um modelo que gera **movimentos em aberto** a cada período; o `RecurringMovementView` traz `value` (o corrente), `suggestedValue` (o que o variável sugere), `launchedInstallments` (a maior parcela já lançada), `nextInstallment`, `launchedInPeriod` e `ended` (inativo ou terminado). **O server omite os campos nulos**: `installments`, `launchedInstallments`, `nextInstallment`, `card` e `reason` chegam ausentes quando não têm valor, então toda conferência é `== null` (o `installmentProgress` e o `isLaunchedIn` de `utils/recurringMovements.ts` fazem isso), nunca `=== null`.

- **Lista.** Abas Ativos, Encerrados e Todos com contagem, o select de tipo sem rótulo ("Todos os tipos", "Receitas" e "Despesas") e a busca por nome, centro de custo ou classificação, tudo no mesmo cartão e na mesma linha; o "Limpar" só aparece com o tipo escolhido (o `SearchControls` tem um slot para o que vem depois das abas). Tudo na URL (`type` como parâmetro extra, `RECURRING_FILTER_KEYS`). A aba é o filtro `ended` do server: Ativos é `ended=false`, Encerrados é `ended=true` (recorrente desativado ou terminado) e Todos não filtra; as contagens das abas seguem a busca e o tipo (`countsFollowFilters`). Abre ordenada pelo nome (`defaultSort` e `default-sort-field="name"`); ordenam o nome, o valor e o tipo de valor (`name`, `value` e `valueKind`), e só a coluna ordenada mostra a seta (`active-sort-icon-only`). O valor sai sem "R$" e com o sinal colado, sem seta (no variável, o `suggestedValue` precedido de "último"); Fixo é o selo neutro e Variável o marca-texto, os dois sem ponto; Situação é "Ativo" (neutro) ou "Encerrado" (apagado). Parcelas mostra "3/12" com a barrinha ao lado (a parcela é `launchedInstallments`, não `nextInstallment`) ou "Indeterminado". O menu "…" tem Detalhes, Editar, Reajustar valor (só no fixo) e Excluir; excluir um recorrente com lançamento responde `recurring-movement-with-launches`, e a mensagem sugere desativar. O botão de criação é "Criar", e vazio, sem resultado e erro usam os textos do mock (`ListState` com `copy`). No celular a linha é compacta (`columns[].mobile`).
- **Formulário.** Título "Novo recorrente" (na edição, "Editando recorrente"). Tipo é o `SegmentedField` Despesa/Receita (um selo na edição), Identificação (nome com o exemplo "Ex.: Videoflix" ou "Ex.: Salário", valor ou "Valor sugerido" no variável, centro de custo e classificação do tipo), Modalidade (dois cartões de escolha, `ChoiceCardsField`: "Fixo, sempre o mesmo valor, com reajustes quando houver" e "Variável, sugere o último valor pago"), Repetição (dois botões de rádio, `RadioOptionsField`: "Número de parcelas", com "Parcelas" e "Parcela atual", e "Prazo indeterminado"; `indefinite` só existe no formulário e vira `installments: null` no payload) e Lançamento (a chave já ligada, `autoLaunch`, com a ajuda "Vence no último dia do período."). O formulário abre como no mock: despesa, fixo, 12 parcelas, parcela atual 1 e lançamento automático. **O cartão não aparece no formulário**: o recorrente só o guarda quando nasce de um parcelamento da compra no cartão, e a edição o devolve como veio (o `RecurringMovementUpdateForm` o exige). Na edição o payload não tem tipo, modalidade, valor nem parcela atual: esses campos ficam travados ou somem (o valor dá lugar à nota sobre Reajustar valor), e o formulário abre com o bloco Situação (`active`, que o server exige). Os erros `classification-type-mismatch` e `inactive-card` saem no alerta do topo.
- **Detalhe e reajuste.** O título leva a parcela atual ("Celular novo 3/12") e as ações do cabeçalho são Excluir, Reajustar valor (só no fixo) e Editar, o primário, nessa ordem (o `DetailCard` tem o slot `middle-actions` entre Excluir e Editar). Identificação em duas colunas (sem o cartão), Valor e repetição (valor atual com "R$", tipo de valor, parcelas com a barra, "Automático ao criar o período" ou "Manual, em lote" e o vencimento) e o Histórico de valores. **Fixo:** enquanto o histórico carrega, o esqueleto da tabela (nunca o texto "Valor fixo." antes de saber), e depois uma tabela paginada de 15 (`GET /{id}/values`, o mais recente primeiro) com "Vale a partir de" em mês e ano (`validFromPeriod.startingAt`, ou a data do registro quando o reajuste não tem período), o valor sem "R$", o motivo ("Valor inicial" no primeiro) e o selo "vigente" na linha que o server marca (`current`); com um registro só, o texto "Valor fixo.". **Variável:** a frase "Valor sugerido no próximo lançamento: 218,35." e a lista do valor de cada período (`GET /{id}/launches`, os 12 mais recentes, `valuePaid` quando pago e `value` quando não). O `ReadjustValueDialog` (`PATCH /{id}/value`, vale a partir do próximo lançamento) mostra o valor atual como exemplo do campo (`placeholder` do `MoneyField`, só aqui) e como ajuda ("Valor atual R$ 55,90."), o motivo com "Opcional. Ex.: reajuste anual" e o botão "Reajustar" com o check; abre pela lista e pelo detalhe pelo `useReadjustValue`, que mostra o toast "Valor reajustado / Vale a partir do próximo lançamento." e recarrega.
- **Toast de criação:** "Recorrente criado / Entra sozinho no próximo período."

**Lançar em lote** (`RecurringLaunchView`, `/financial/recurring-movements/launch`, nome `recurring-movements.launch`, breadcrumb "Lançando"; o `crudRoutes` ganhou `extra` para acrescentar essa rota ao registro dos recorrentes). Usa o `useListFilters` direto, com o extra `period` (o mock chama de `periodo`; os parâmetros do client são em inglês), `page`, `size` e `sort`, e o store `recurringLaunch`, que guarda também a seleção (que atravessa as páginas, e some ao trocar de período) e os valores digitados. A tabela não ordena (abre pelo nome) e tem as colunas Recorrente, Tipo de valor, Valor (R$) e Situação. O período abre no aberto **seguinte** ao que contém hoje (`nextOpenPeriod`; sem seguinte, o atual) e um `period` da URL que não está entre os abertos cai nele; a ajuda ao lado diz quando vencem ("Vencem em 31/12/2026.") ou, quando tudo o que veio já foi lançado, "Neste período não sobrou nada manual para lançar.". A lista é a de `findAll` com `ended=false` e `financialPeriod`; `launchedInPeriod` marca a linha como lançada (esmaecida, caixa desabilitada, "Lançado automaticamente" quando o recorrente é automático e "Já lançado" quando não), e o selo da parcela ("12/12") só aparece nos parcelados. Clicar na linha marca ou desmarca. O variável disponível tem o campo de valor na linha (`MoneyInput`, com o "R$" ao lado, começando no `suggestedValue`; o payload só leva `value` nos variáveis). A barra do rodapé (`sticky`) diz "Nenhum selecionado" e, com marcados, "2 selecionados · efeito no período −274,02" (receita positiva, despesa negativa, sem "R$"); o botão é "Lançar recorrentes" e, com marcados, "Lançar 2 recorrentes". No celular a lista vira um cartão só, com o nome e o valor na mesma linha e, embaixo, o tipo de valor ou a situação; ali o valor do variável não tem campo, como no mock. O server devolve `launched` e `skipped` como listas: o toast conta `launched` e um aviso lista os `skipped` com o motivo (`recurrent-movement.skipped.*`); depois a tela vai para os movimentos do período. Sem período aberto a tela só oferece "Criar período".

**Criação do período e cartão sugerido.** `POST /registration/financial-periods` responde `201` com `{ recurringLaunch }` além do `Location`: o `financialPeriodsApi.create` devolve `{ id, recurringLaunch }` e o store guarda o relatório. O formulário de período tem, ao lado (abaixo do formulário até 1280px), o quadro "Ao criar este período", de `GET /financial/financial-periods/creation-preview` (`recurringMovements` com a parcela que vai entrar, e `invoices`, os cartões que ganham fatura): o store o carrega ao abrir e de novo depois de criar, porque as parcelas andaram, e sem dado (ou se a chamada falha, que é `silent`) o quadro some. O toast é "Período criado / 8 recorrentes lançados e 3 faturas abertas.": os recorrentes vêm do `recurringLaunch` e as faturas do quadro que estava na tela ao criar (`openedInvoices`). Um erro de lançamento desfaz a criação inteira, e o alerta do topo diz para corrigir ou desativar o recorrente. O movimento lançado por um recorrente traz `recurringMovement { id, name, card }` na `MovementView`: o detalhe mostra o link "Recorrente" e o `PayMovementDialog` abre em "Cartão" com `card` quando há `suggestedCard`. A listagem de movimentos não traz esse dado, então o "Pagar" da lista busca o movimento antes de abrir o diálogo (`useMovementActions.openPayWithSuggestion`).

**Compra parcelada.** O formulário da compra no cartão tem a seção Parcelamento (`InstallmentPurchaseSection`): a chave "Compra parcelada", o número de parcelas (abre em 12), o valor da parcela e o alerta "Como a parcela entra", com o atalho "Lançar a primeira parcela" para o lote. Ligada a chave, o botão é "Criar parcelamento" e o formulário cria **o recorrente** (`POST /financial/recurring-movements`: despesa, fixo, o valor da parcela, as parcelas, `firstInstallment: 1`, `autoLaunch: true` e o `card`), não uma compra: o valor da compra deixa de ser obrigatório, e o toast é "Parcelamento criado / Entra sozinho no próximo período." (o `useCrudForm` ganhou `successTitle`). A parcela do período atual entra pelo lote.

### Administração de usuários

Tela em `src/views/configuration/users/` (`UserListView` e `UserFormView`), sob `/configuration/users`, `.../create` e `.../:id/update` (nomes `users`, `users.create` e `users.update`; sem tela de detalhe, por isso as rotas são escritas à mão em `configurationRoutes.ts` e não saem do `crudRoutes`). A role `ADMINISTRATION` vem do registro `/configuration`. A tela segue o padrão de listagem e formulário (veja [Cadastros](#cadastros)) com o desenho do mockup de usuários (#78). O store, a API e os esquemas continuam.

- **Lista.** O nome e o e-mail ficam na mesma célula, com o `UserAvatar` (as iniciais do primeiro e do último nome) e o "(você)" na linha de quem está logado; as áreas de acesso saem como `Badge` `outline` (mono), na ordem fixa de `components/users/roles.ts` (Dashboards, Financeiro, Cadastros e Configurações; o server não garante ordem), e a coluna Situação é a do `ItemsTable`. A ordenação por nome vale; a por e-mail saiu com a junção das duas colunas. A coluna Situação do `ItemsTable` (ativo e inativo) dá lugar às colunas Status (`UserStatusBadge`) e TOTP ("Ativo", "Não configurado" ou "—" para o pendente). As abas são Aprovados, Pendentes, Bloqueados e Todos (`USER_STATUS_OPTIONS`), com contagem, e a tela abre em Aprovados, a menos que a URL traga `?status=PENDING|APPROVED|BLOCKED|ALL` (o link do e-mail de cadastro pendente usa `/configuration/users?status=PENDING`): o estado da URL vale como em todas as listas (veja [Filtros na URL](#filtros-na-url); valor de `status` desconhecido abre em Aprovados e a aba trocada vai para a URL); sem sessão o guard já manda para `/login?redirect=<caminho com a query>`; o `ListState` cobre vazio, sem resultado e erro de carga. A ordem é a de todas as listas (criação, do mais novo ao mais velho): o mockup pedia os pendentes primeiro, mas a regra do produto vale, então os pendentes ganham o marca-texto na borda da linha (`marked-row` do `ItemsTable`, que põe o `data-state="selected"`) e um aviso acima da tabela ("N contas aguardando aprovação", com "Ver pendentes") enquanto há pendentes e a aba não é a deles. A aba Pendentes vazia e sem busca diz "Nenhuma conta aguardando aprovação" (no lugar do "nada encontrado" genérico) e uma conta sem áreas mostra "Nenhuma ainda" na coluna. O menu "…" da linha é o `UserRowActions`: Aprovar (só do pendente, e também um botão na linha no desktop), Editar, Bloquear (do aprovado), Desbloquear (do bloqueado), Redefinir senha, Resetar TOTP (só com TOTP ativo) e, depois do separador, Remover; no celular (abaixo de 768px) vira uma folha por baixo (`Sheet`) com os mesmos itens. Bloquear, desbloquear e resetar o TOTP pedem confirmação (`useConfirmDialog`) e, como as outras ações, ficam desabilitados na própria conta. Aprovar abre o `ApproveUserDialog`, que pede as áreas de acesso (uma ao menos, vindas pré-marcadas das que a conta já tem): o auto-cadastro nasce sem área nenhuma, então o `approve` do store manda as áreas no corpo do próprio `PATCH /approve` (`{ roles }`), numa chamada só, e o server grava as áreas e aprova na mesma transação: uma falha deixa a conta como estava (pendente e sem as áreas novas). Um `400` (`field-validation-failed`, áreas ausentes ou desconhecidas) vira a mensagem "Alguma informação está ausente ou inválida". O `useUserActions` reúne as cinco ações (confirmação, chamada, toast e recarga) para a lista e a coluna lateral do formulário. Um `409 invalid-user-status-transition` (a conta mudou de status com a tela aberta) vira a mensagem "Atualize a lista".
- **O contrato do server tem armadilhas que a tela já cobre.** O `POST` exige senha (`UserCreateForm.password`) e só envia o e-mail de ativação com `sendActivationEmail: true`, então o formulário de criação pede a senha e liga o envio por padrão (um `StatusToggle`). A `UserView` devolve `authorities`, mas os formulários enviam `roles`: o `schemas/userSchema.ts` faz a troca (`toUserFormValues`). Um usuário novo nasce inativo até ativar a conta; a lista filtra por status de aprovação e não por ativo, então nenhuma aba esconde esse usuário (veja a **Lista**). O e-mail não muda na edição (o `UserUpdateForm` nem o tem). O `409` de e-mail repetido vem como `parameters['user.email']`, traduzido em `error.conflict.user.email`.
- **Formulário.** Criar tem três seções (Dados, Acesso e Áreas de acesso). Editar empilha Dados e Áreas de acesso (`stacked`), mostra o nome no título, o e-mail abaixo e a situação ao lado (`badge`), deixa o e-mail só para leitura e abre com o bloco Situação (`StatusSection`, "Cadastro ativo", `active`) antes de Dados. A coluna lateral (`aside`) mostra os dados da conta (situação, idioma e áreas) e as ações Redefinir senha e Excluir usuário; depois de excluir, o formulário é limpo antes de voltar à lista para o "Sair sem salvar?" não aparecer. A tela só mostra o que a `UserView` devolve (veja a **Coluna lateral**).
- **Sem ação sobre a própria conta.** A linha do usuário logado (`email` igual ao de `auth.session`) tem o menu com os três itens desabilitados e "Sua conta" no lugar do nome do menu; no formulário de edição da própria conta, as duas ações da coluna lateral ficam desabilitadas. É só UX: o server recusa a ação sobre a própria conta com `400` `self-action-not-allowed` (`SelfActionGuard`), e a tela só evita o clique inútil.
- **Confirmação em toda ação.** Criar e salvar passam pela opção `confirm` do `useCrudForm` (roda antes da chamada e, se recusada, não grava, não mostra o aviso de sucesso nem limpa o formulário), com a pergunta citando o nome ("Criar o usuário “Ana”?") e o botão repetindo o verbo; excluir usa o `confirmRemoval` (na lista, via `useCrudList`, e na coluna lateral). Redefinir a senha é um diálogo (`components/users/ResetPasswordDialog.vue`) com senha e confirmação; o botão do diálogo é a confirmação, e o sucesso vira o toast "Senha redefinida". A senha vai com `temporary: true` (o server ignora o campo hoje, por isso a tela não oferece a opção de pedir nova senha no próximo login) e a troca encerra as sessões abertas do usuário, porque sobe o `credentials_version`.
- **Áreas de acesso.** O `RoleSelectField` mostra cada role como um cartão com a descrição (`users.role-description.*`), a partir do que o `GET /administration/roles` devolve, carregado pelo `findRoles` ao abrir o formulário; exige ao menos uma ("Escolha pelo menos uma área.", pela regra `roles-required` do `zodErrorMap`). `ADMINISTRATION` aparece como "Configurações". Quando as roles de alguém mudam, a próxima requisição dele já responde `403` `forbidden` nas áreas perdidas (o server confere a role no banco a cada chamada); o `apiErrorHandler` leva à tela `403`.
- **Coluna lateral.** Mostra também o status de aprovação e o TOTP e traz as ações Aprovar, Bloquear, Desbloquear e Resetar TOTP (as mesmas da lista, com o `useUserActions` recarregando o registro). O server não diz quantos dispositivos confiáveis a conta tem, então o mockup (que mostra a contagem) ficou sem ela.

### i18n (`src/locales/`)

Todo texto que o usuário vê passa pelo vue-i18n (`t('chave')` no `<script setup>`, `$t('chave')` no template), em modo de composição (`legacy: false`). Os catálogos ficam em `src/locales/pt_BR.json` e `src/locales/en_US.json`, registrados como `pt-BR` e `en-US`. O `pt-BR` é o idioma padrão e o de fallback, e os dois catálogos têm **exatamente as mesmas chaves e os mesmos parâmetros** (`{name}`, `{count}`…): o `locales/index.test.ts` falha se uma chave existe só num deles, se o inglês tem uma mensagem vazia ou se os parâmetros divergem. Uma chave nova entra nos dois arquivos no mesmo PR, e a pluralização (`um | vários`) segue a mesma forma nos dois. Os formatos de número (`currency`, `decimal`, `percent`) e de data (`short`, `long`) estão em `src/locales/index.ts`, um conjunto por idioma: o idioma troca separadores e a ordem das datas, **mas a moeda é sempre o real** (o `currency` do `en-US` também é BRL e sai `R$1,234.50`), porque a moeda é do dinheiro do usuário e não do idioma. As constantes e funções puras dos idiomas ficam em `src/locales/languages.ts`: `SUPPORTED_LOCALES`, `DEFAULT_LOCALE`, o mapa entre o `Language` do server (`PT_BR`, `EN_US`) e o locale do client (`LANGUAGE_LOCALES`, `LOCALE_LANGUAGES`) e o `detectBrowserLocale`, que casa `pt*` com `pt-BR` e `en*` com `en-US`.

**Qual idioma vale.** O `createI18n` nasce sempre em `pt-BR`; quem escolhe o idioma de verdade é o store `language` (`stores/language.ts`), instanciado no `main.ts`, na ordem: o `language` do perfil da sessão (`auth.session.language`), senão a escolha guardada em `localStorage` (`webbudget.language`, lida e gravada dentro de `try/catch`), senão `navigator.languages` (cai em `navigator.language` quando a lista não existe), senão `pt-BR`. Um idioma do perfil que o client não conhece é ignorado e o idioma atual continua. O store aplica o locale ao `i18n.global.locale` e ao atributo `lang` do `<html>`, e guarda no `localStorage` o idioma de quem escolheu e o do perfil que a sessão trouxe, para a tela de login depois do logout abrir no mesmo idioma; o que o navegador sugere nunca é gravado.

**O seletor** é o `LanguageSwitch` (`components/layout/`, o mesmo desenho do `ThemeSwitch`: `pt-BR` e `en-US`, com o nome completo no `aria-label`): `select(locale)` sem sessão troca e guarda na hora; com sessão (inclusive a pendente) chama o `PATCH /auth/language` e só troca depois que o server responde, porque o locale vem da `auth.session` (atualização pessimista, como no resto; se a chamada falha o idioma não muda e o toast padrão aparece). O cadastro manda o idioma da tela em `defaultLanguage`, então o e-mail de ativação já sai nele. **Nos testes**, o `src/test/setup.ts` fixa `navigator.languages` em `['pt-BR']` (o jsdom é `en-US`) e, a cada teste, devolve o `i18n` ao `pt-BR` e limpa o `localStorage` e o `lang`: um teste que muda o idioma não vaza para o seguinte.

## Autenticação

A autenticação é por sessão no servidor (#26): o cookie de sessão é do navegador e o client nunca o lê, nunca guarda credencial e nunca recebe nem guarda token. O store `auth` só mantém a `SessionResponse` que o server devolve (`name`, `email`, `status`, `language` e `roles`). O `restoreSession()` pergunta ao `GET /auth/session` se a sessão continua viva e responde `false` em qualquer falha.

**Esconder um botão ou redirecionar uma rota é UX, não controle de acesso.** O server confere cada permissão por conta própria em cada requisição. Um `v-if` por role ou um redirecionamento do router melhora a experiência de quem usa o sistema direito e não faz nada contra quem chama a API direto, então nunca raciocine sobre o que o client esconde como se fosse a fronteira de segurança.

O guard de rotas (`router/guard.ts`) confere a sessão e a role (veja [Layout e rotas](#layout-e-rotas)). Uma sessão cujo status não é `APPROVED` (o `GET /auth/session` responde 200 para ela, só as outras rotas respondem 403 `pending_approval`) é mandada para `/pending-approval` em qualquer rota privada, e o login que termina numa sessão assim vai para lá em vez de ir ao destino.

**Fim de sessão.** O `auth.logout()` e o `auth.expireSession(reason)` navegam para o `/login` primeiro e só então limpam a sessão e os stores (`endingSession` fica `true` no meio), para que a tela que está aberta nunca renderize sem sessão. Quem sai por `expireSession` leva `?reason=expired|inactivity` e, se a tela era privada, `redirect=` com ela; a `LoginView` mostra o aviso da razão como toast, sem mexer no layout, e não manda o usuário de volta ao app enquanto `endingSession` é `true`. `expireSession` não faz nada sem sessão ou com um fim de sessão em curso, e o `POST /auth/logout` que ele dispara é `silent` e ignora a falha.

**Logout por inatividade.** O `useInactivityLogout`, iniciado no `App.vue`, confere a cada 30 s (e quando a aba volta a ficar visível) se a última resposta do server (`lastServerActivityAt`) tem 30 minutos ou mais, o mesmo timeout de sessão do server, e então chama `expireSession('inactivity')`. Só vigia enquanto há sessão.

**CSRF.** O server (#26) exige o header `X-XSRF-TOKEN`, igual ao cookie `XSRF-TOKEN`, em toda escrita, até nas anônimas (`POST /auth/login`, `PATCH /accounts/*`); sem ele responde `403` `invalid-csrf-token`, não `401`. O axios do `apiClient` lê o cookie e manda o header sozinho (mesma origem). O cookie só nasce depois de algum `GET`, então um interceptor de requisição do `client.ts` dispara um `GET /auth/session` `silent` antes de qualquer escrita feita sem o cookie (as telas de recuperação de senha e de ativação, abertas direto pelo link do e-mail, não têm outro `GET`), e escritas simultâneas dividem esse mesmo `GET`.

### Telas de autenticação e de erro

As rotas públicas ficam em `router/publicRoutes.ts`. O login é `/login` (as etapas de conta são da `LoginView`), o aguardando aprovação é `/pending-approval` (dentro do `AuthLayout`); esqueci a senha, recuperação e ativação ficam sob `/auth` (`/auth/forgot-password`, `/auth/recover-password`, `/auth/account-activation`), dentro do `AuthLayout`. **Os dois últimos caminhos e os parâmetros `token` e `email` são o contrato dos emails que o server envia** (o back-end da v4 monta `${frontendUrl}/auth/...?token=...&email=...`): não os renomeie sem mudar o server. As telas de erro são `/error/forbidden` (`403`), `/error/not-found` (`404`) e `/error/server-error` (`500`), sem layout, e uma rota coringa pública (`not-found`) mostra a de 404 para qualquer caminho desconhecido.

- **Layout:** o `AuthLayout` tem a folha pautada (`AuthAside`) à esquerda a partir de `lg` e, à direita, a coluna da etapa de até 400px com o `RouterView`; abaixo de `lg` a folha some e a marca vai para o topo da coluna. O seletor de idioma (`LanguageSwitch`) fica no canto superior direito da coluna, então vale para login, cadastro, recuperação, ativação e aguardando aprovação. O `publicRoutes.ts` carrega o `AuthLayout` sob demanda: um import estático fecha o ciclo `AuthLayout` → `LanguageSwitch` → store `language` → store `auth` → router → `publicRoutes`. Cada etapa é uma `AuthStepHeader` seguida do conteúdo, e as etapas de resultado (e-mail enviado, conta ativada, link inválido) abrem com um `AuthStatusIcon`. As etapas da conta (cadastro, TOTP e vínculo com o Google) entram na mesma coluna: a `LoginView` troca o componente da etapa, e o aguardando aprovação é a rota pública `/pending-approval` (`PendingApprovalView`).
- **Login:** `POST /auth/login` com `{ email, password }` (mais `totpCode` e `trustDevice` na etapa do código). A `LoginView` troca as cinco etapas (`credentials`, `register`, `enroll`, `totp` e `link`) e o `composables/useLoginFlow.ts` guarda a máquina de estados; o fim do fluxo (`finish`) manda a sessão `APPROVED` para o `redirect` (filtrado) ou a raiz (que o guard leva à primeira seção permitida) e qualquer outra para o `/pending-approval`. O `CredentialsStep` só tem o formulário e emite `submit`. Credencial ou conta recusada (401 e 403) e o limite de tentativas (429) aparecem num `Alert` acima do formulário, nunca em toast: o `describeApiError` devolve `null` para o 401 e o 403 e o `apiErrorHandler` ignora o 429 `too_many_login_attempts`, então o plugin não mostra nada, e as mensagens (`login.failure.*`) são as mesmas para `invalid-credentials`, `account-disabled` e 403, para não revelar se o e-mail existe; qualquer outra falha já virou o toast padrão e a view não repete. O botão fica em "Entrando…" e o formulário desabilitado só enquanto o `POST` roda (o `loading` do store também vale durante o `restoreSession`, por isso não serve). Ao montar, a tela pergunta ao `restoreSession()` e, com sessão viva, segue direto para o destino. O botão "Entrar com Google" e o divisor "ou" só aparecem quando o `useAuthConfig` diz que o Google está ligado (o link vai para `/private/oauth2/authorization/google`), e o "Criar conta" só com a prop `registrationEnabled` do `CredentialsStep`, que a `LoginView` liga.
- **O fluxo tem armadilhas do server que o client cobre.** O login responde 200 (sessão) ou 202 (`needs_enrollment` ou `needs_totp`), e quem decide é o código HTTP (veja `api/auth.ts`). **O server não guarda estado entre as etapas**: cadastrar o TOTP, confirmá-lo e repetir o login com o código reenviam e-mail e senha, e o vínculo com o Google reenvia a senha. Por isso o `useLoginFlow` guarda as credenciais em variáveis comuns do composable, nunca em ref, store, URL ou storage, e as esquece ao terminar, ao trocar de conta e ao desmontar. O envio é travado enquanto outro está em curso (o `complete` das caixas do código pode disparar mais de uma vez). Uma conta sem TOTP passa pelo cadastro antes de qualquer aprovação, então o caminho real do auto-cadastro é: cadastro, e-mail de ativação, ativação, login, QR code e primeiro código, e só então a sessão `PENDING` cai no `/pending-approval`; antes de ativar, o login responde 401 `account-disabled`, que aparece como credencial incorreta.
- **Cadastro (`RegisterStep`).** Nome, e-mail e senha com as regras de `utils/passwordRules.ts` mais o limite do server de 72 bytes UTF-8 (`fitsPasswordBytes`, que conta bytes, não caracteres). O `POST /auth/register` responde 201 mesmo para um e-mail que já existe (para não revelar quem tem conta), então o client segue sempre para o `/pending-approval`, que mostra o e-mail digitado (`auth.registeredEmail`, só em memória) e lembra do link de ativação. O 429 `too_many_registration_attempts` vira o alerta da etapa.
- **Aguardando aprovação.** A tela serve a quem acabou de se cadastrar (sem sessão) e a quem tem sessão `PENDING`. "Voltar para o login" **encerra a sessão** quando há uma (`auth.logout()`); sem isso a `LoginView` restauraria a sessão e o guard devolveria a pessoa para cá, num laço.
- **TOTP.** `TotpEnrollStep` (QR code do server, chave em grupos de quatro com "Copiar chave" e o primeiro código) e `TotpVerifyStep` (código e "Confiar neste dispositivo", **desligado por padrão**: confiar é uma escolha de quem está no aparelho). O `TotpCodeInput` são as seis caixas do Reka (`PinInput`, só dígitos, colar o código inteiro, `autocomplete="one-time-code"`) e avisa `complete` uma vez por código, no sexto dígito, para as etapas enviarem sozinhas. Código errado (401 `invalid_totp_code`) deixa as caixas vermelhas, limpa o código e devolve o foco à primeira; 429 `too_many_totp_attempts` vira o alerta da etapa; 401 de credencial (a senha mudou no meio) volta às credenciais; falha de rede mantém a etapa.
- **Google.** Sem credencial real, o botão só aparece com `googleAuthEnabled`. A volta do Google traz `?error=email_in_use&linkToken=…` (sem o e-mail: o texto da etapa não o cita), `?error=email_in_use` sem token ou `?error=oauth_failed`; qualquer `error` desconhecido vira a mensagem genérica, nunca o texto cru. O `linkToken` e o `error` saem do endereço assim que lidos (`router.replace`), para não ficar no histórico. Se o vínculo exige TOTP, o server responde 202 e a etapa troca a senha pelo código (o `useLoginFlow` reenvia a senha). **O server queima o token numa senha errada, num código errado e num token inválido**; por isso a etapa não oferece repetir: mostra "O vínculo não foi concluído" e manda entrar com o Google de novo. 429 e falha de rede mantêm o token e a etapa.

### Dispositivos confiáveis

O item "Dispositivos confiáveis" do menu do usuário (e o botão do rodapé da folha do celular) abre o `TrustedDevicesDialog`, montado uma vez no `App.vue` e aberto por `useTrustedDevicesDialog()`. Ele lista os dispositivos (rótulo, último uso e quando foi confiado) pelo store `trustedDevices` e revoga um ou todos; **revogar é sempre uma chamada ao server** (`DELETE /auth/trusted-devices[/{id}]`), porque o cookie é `HttpOnly`. A confirmação de revogar acontece dentro do próprio diálogo (um segundo painel), não num `AlertDialog` por cima dele. Duas diferenças do mockup: o `TrustedDeviceView` não diz qual é o dispositivo atual (o cookie é `HttpOnly`), então não há o selo "Este dispositivo" nem a confirmação especial dele, e a confirmação avisa em texto que, se for o aparelho em uso, o código volta a ser pedido.
- **Esqueci a senha, recuperação e ativação:** usam o store `account`; falhas já viram o toast padrão (o `invalid-token` do 400 diz "Token inválido ou expirado"), então só o sucesso é tratado na tela. O esqueci a senha troca o formulário pela etapa "Confira seu e-mail" depois do envio. A ativação tem três estados explícitos (`activating`, `success`, `error`), com o e-mail do link na etapa de sucesso, e `queryValue` (`utils/queryValue.ts`) lê `token` e `email` da query.
- **Recuperação:** a senha precisa cumprir as regras de `utils/passwordRules.ts`, e a lista `PasswordRequirements` (o mesmo `passwordRequirementStatus` do schema) marca cada requisito enquanto a pessoa digita. O `refine` da senha usa `params: { i18n: 'password-requirements' }`. A confirmação precisa ser igual à senha: o `refine` do `recoverPasswordSchema` marca o issue com `params: { i18n: 'password-mismatch' }`, que o `zodErrorMap` traduz; uma regra cruzada nova segue o mesmo caminho. O server hoje só exige senha não vazia, então a regra é do client.
- **Testes de formulário:** o vee-validate valida de forma assíncrona; depois de `trigger('submit')` use `await settle()` (`src/test/settle.ts`) em vez de um único `flushPromises()`.

## Estilos

O estilo é o **Caderno verde** (#66, #73), sobre o Tailwind 4, sem arquivo de configuração em JavaScript: o plugin `@tailwindcss/vite` está no `vite.config.ts` e o `src/assets/theme.css` importa o Tailwind e define os tokens (`--background`, `--primary`, `--sidebar` e companhia) para o claro e o escuro, mais o `@theme inline` que os expõe como classes. Mexer no visual é mexer nos tokens desse arquivo; entre os temas só mudam luminosidade e croma, nunca o matiz. Os mockups (linguagem visual, shell, login, usuários e listagem/formulário/detalhe) estão linkados na #73 e na #66.

- **A linguagem:** IBM Plex Sans na interface e IBM Plex Mono nos valores, datas, códigos e na marca; raio de 3px (`--radius`), bordas de 1px, controles de 36px (`h-9`), linhas de tabela de 48px e escala de 4px. Sombra só em menu, popover, toast e diálogo; cartão não tem sombra. Ícones Lucide em 16px, com o traço de 1,75 aplicado por `svg.lucide` no `theme.css`, sempre ao lado de texto.
- **Fontes pelo bundle:** `@fontsource-variable/ibm-plex-sans` e `@fontsource/ibm-plex-mono` (400, 500 e 600), importados no `main.ts`. Não use Google Fonts nem outra fonte externa.
- **Tokens além do shadcn-vue:** `--destructive-foreground`, `--highlight` e `--highlight-foreground`, `--income`/`--income-muted` e `--expense`/`--expense-muted`. O **marca-texto** (`highlight`) só aparece no que pede atenção (usuário pendente, item ativo do menu, linha selecionada) e nunca em texto de tabela; no escuro ele escurece para o texto claro continuar legível. **Dinheiro** de receita e despesa sempre leva sinal (`+`/`−`) ou seta, nunca só a cor (veja `CurrencyDisplay` com `signed`); o extrato é a exceção decidida pelo usuário: o sinal só aparece no valor realmente negativo, e a cor (`tone`) mais a seta dizem crédito ou débito. O utilitário `marker` desenha o traço de marca-texto atrás do texto.
- **Variantes dos componentes** (`components/ui/`): `Button` (`default`, `secondary`, `outline`, `ghost`, `destructive`, `link`; tamanhos `sm`, `default`, `lg` e `icon`), `Badge` (`approved`, `pending` e `blocked` com o ponto, `neutral` e `outline` em mono), `Alert` (`default`, `destructive` e `attention`; o `ServerErrorAlert` é um `Alert` destrutivo), `Table` (cabeçalho de 40px em versalete de 11px, células de 48px com 16px de lado e texto de 15px; `data-state="selected"` na `TableRow` marca a linha com o marca-texto), `Switch` de cantos retos. O bloco do campo (`FormItem`) alinha pelo topo (`content-start`) para a mensagem de erro crescer para baixo sem desalinhar a linha; `Input` e `Textarea` ficam em `text-base` no celular e `text-sm` a partir de `md`, para o iOS não dar zoom ao focar.
- **Marca:** `BrandMark` e `BrandWordmark` (`components/brand/`) seguem o tema. O `src/assets/brand/mark.svg` é o símbolo “wB” com as letras em contorno e as cores fixas, para uso fora do app; o `public/favicon.svg` usa só o “B”, porque o “wB” a 16px não se lê. Para gerar o contorno de outra palavra, converta com o opentype.js a partir do arquivo `.woff` da fonte, sem acrescentar a dependência ao projeto.
- **Classes do Tailwind primeiro, CSS próprio só no que ele não oferece.** Não crie classe CSS própria quando um utilitário resolve (`bg-highlight/80`, `before:*`, `size-[22px]`, valores arbitrários). O que é exclusivo de um componente e o Tailwind não expressa vai em `<style scoped>` no próprio componente (hoje só o papel pautado do `AuthAside`, um `repeating-linear-gradient`); o que é reaproveitado fica no `theme.css` (o utilitário `marker`). O `bg-white` do QR code do `TotpEnrollStep` é de propósito: o código precisa de fundo claro para ser lido, no tema escuro também.
- **Use os tokens, não cores fixas.** `bg-background`, `text-muted-foreground`, `border` e afins trocam sozinhos com o tema. Não use `text-white`, `bg-black/…` nem as cores do Tailwind (`emerald-600`): o texto sobre `destructive` é `text-destructive-foreground`, o fundo do diálogo é o `--popover`, e o status vem das variantes do `Badge`.
- **O tema escuro é a classe `dark` no `<html>`.** O store `appearance` (`stores/appearance.ts`) guarda o modo (`light`, `dark` ou `system`; `dark` é o efetivo, calculado, e `setMode` troca) em `localStorage` (`webbudget.appearance`, formato `{ "mode": "system" }`) e aplica a classe; ele é instanciado no `main.ts`, para valer também nas telas públicas. Sem escolha o modo é `system`, que segue `prefers-color-scheme` ao vivo. O formato antigo `{ "dark": true }` vira `dark`; `{ "dark": false }` vira `system`, porque o store antigo o gravava em toda partida. A troca fica no menu do usuário (`ThemeSwitch`) e no rodapé do Sheet.
- **Ícones vêm do `lucide-vue-next`.**
- **Componente novo do shadcn-vue:** o `components.json` já está pronto, mas a CLI só acha o alias `@/*` com um `compilerOptions.paths` no `tsconfig.json` da raiz, que aqui só tem referências. Acrescente-o à mão antes do comando, rode `pnpm dlx shadcn-vue@latest add <componente>` e **desfaça o `tsconfig.json`** depois. Confira o resultado: a CLI importou o `cn` de um pacote `cn` e os ícones do `@lucide/vue` (troque por `@/lib/utils` e `lucide-vue-next` e tire os dois do `package.json`), e o código gerado vem com aspas duplas (rode o Prettier nele).
- **Gráficos:** o `chart.js` não está instalado. A v4 não tem gráfico em lugar nenhum (o `FinancialLayout` dela só tem ícones de gráfico); quando uma tela precisar de um, o `chart.js` entra junto com ela.
